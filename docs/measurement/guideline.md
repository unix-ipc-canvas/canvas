# IPC 선택 가이드라인 (보고서 6.6절 원본)

[문서 안내](../../README.md#관련-문서)

측정용 컴퓨터(Intel Core 5 120U, Ubuntu 26.04.1, 커널 7.0)에서 우리가 구현한 세 전송 계층을 잰 결과로 정리했다. 수치는 [1단계 측정 결과](stage1.md)(반복 20번), [2단계 측정 결과](stage2.md), 그리고 그 안의 [설계 개선 실험](stage2.md#설계-개선-실험-t6)에서 왔다. 다른 컴퓨터나 다른 구현에서는 순위가 달라질 수 있다.

## 한눈에 보기

| 상황 | 고를 것 | 근거 (측정값) |
| --- | --- | --- |
| 메시지 16KB 이하, 한 번의 왕복 지연이 중요 | 아무것이나. 구현이 쉬운 pipe나 mq | 클라이언트 1의 지연 중앙값 64B~16KB가 pipe 9.93~21.12, mq 8.10~16.75, shm 9.57~16.02µs다. 실행 사이 편차(54~124%)가 차이보다 커 모두 `≈`다. 응용의 DRAW·16KB SNAPSHOT 지연도 `≈`다 |
| 작은 메시지를 많이 보냄 (처리량) | mq | 1단계 64B 처리량은 mq 47.5, shm 32.8, pipe 28.3MB/s다. 응용의 DRAW만 보낼 때 초당 요청은 mq 362,701, pipe 273,675, shm 252,600이다. 메시지 경계를 커널이 지켜 주어 구현도 간단하다 |
| 64KB 이상 큰 데이터 | shm | 1단계 1MB 처리량은 shm 9,388, mq 1,862, pipe 1,069MB/s다. 응용의 1MB SNAPSHOT은 초당 shm 10,246, mq 3,816, pipe 1,422다. 메시지 하나의 컨텍스트 스위치가 크기와 관계없이 3번이다(pipe는 1MB에서 66.8번) |
| 클라이언트가 많고 메시지가 작음 | pipe나 mq. shm은 피함 | 64B·클라이언트 8의 지연은 shm 38.10µs로 가장 길다(mq 23.09, pipe 26.84). 응용의 클라이언트 8 처리량도 shm 76,560으로 가장 낮다. 모든 클라이언트가 요청 링 하나를 세마포어로 번갈아 쓴다 |
| 우리 응용 (DRAW 90%, 클라이언트 4~8) | pipe나 mq | 묶지 않으면 셋의 차이가 편차 안이다. P코어에 묶으면 `pipe > mq > shm`(277,392 / 260,917 / 183,124)이다. shm은 큰 SNAPSHOT이 많을 때(DRAW 80% 이하)만 앞선다 |

## IPC별 주의할 점

- **pipe(FIFO)**: 64KB(버퍼 크기)를 넘는 응답은 버퍼마다 양쪽이 잠들고 깨어, 1MB 지연이 mq의 약 3배다(1,159.0 vs 393.9µs). `PIPE_BUF`(4096B)를 넘는 요청을 여러 클라이언트가 보내면 순서가 보장되지 않는 잠금 때문에 최대 지연이 상위 99%의 205~1,613배로 튄다.
  - 버퍼를 키우는 것(`F_SETPIPE_SZ`)은 만능이 아니다. 1MB로 키우면 64KB~256KB 응답과 섞인 처리량은 1.14~1.30배 좋아지지만, 1MB 응답의 지연은 1.36~1.60배 나빠졌다.
- **mq**: 메시지 하나의 한도(`msgmax`, 기본 8KB)가 있어 큰 데이터는 조각으로 나눠야 한다. 한도를 올리면 처리량이 1.5~2배로 늘지만 클라이언트 1의 지연은 2~3.5배로 늘었고 관리자 권한이 필요하다.
- **shm**: 복사가 한 번이라 큰 데이터에 강하다. 대신 동기화(세마포어, 링의 head·tail)를 직접 만들어야 하고, 상대가 죽은 것을 커널이 알려 주지 않는다. 링 크기만큼 메모리를 쓴다.
  - 쓰임에 맞게 링을 줄이면 된다. 요청이 작은 우리 응용은 요청 링을 메시지 1개 분량으로 줄여도 처리량이 그대로였고, 최대 RSS는 서버 0.63~0.87배, 클라이언트 0.63배로 줄었다.

## 고르기 전에

- 이 컴퓨터에서는 IPC 차이보다 CPU 배치와 주파수의 영향이 더 컸다. 워커 4에서 처리량이 워커 8의 절반 아래로 떨어진 것은 IPC가 아니라 CPU 주파수(1,374 vs 2,718MHz) 때문이었다. 같은 조건을 P코어에 묶으면 편차가 2~3%로 줄었다.
- 그래서 실제로 돌릴 컴퓨터에서, 실제 메시지 크기 분포로, 여러 번 반복해서 재고 고른다. 몇 번 잰 값의 순위는 반복을 늘리면 바뀔 수 있다(1단계 반복 5번 → 20번에서 클라이언트 2·4·8의 순위 42칸 중 14칸이 바뀌었고, 대부분 4KB 이하였다).
