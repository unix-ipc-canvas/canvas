## 결과

### 16KB 이하: 세 IPC가 구분되지 않는다

- 클라이언트 1의 왕복 지연 중앙값은 64B~16KB에서 pipe 9.07~21.25µs, mq 8.13~19.30µs, shm 8.47~12.89µs다. 실행 사이 편차((최대 − 최소) / 중앙값)가 9~85%로 IPC 사이의 차이보다 커서 순위는 모두 `pipe ≈ mq ≈ shm`이다.
- 처리량(동시 요청 16)은 4KB 이하에서 mq가 가장 높거나 shm과 같다. 64B에서 mq 44.8MB/s, shm 32.2MB/s, pipe 29.7MB/s다.
- 메시지 하나의 자발적 컨텍스트 스위치(클라이언트 + 서버)는 네 IPC 모두 3번이고, 64B의 CPU 시간은 10.7~13.3µs로 비슷하다.

### 64KB 이상: pipe가 가장 느리고, 처리량은 shm이 크게 앞선다

| 크기 | 지연 중앙값 pipe / mq / shm (µs) | 지연 순위 | 처리량 pipe / mq / shm (MB/s) | 처리량 순위 |
| --- | --- | --- | --- | --- |
| 64KB | 80.0 / 32.1 / 36.7 | mq ≈ shm < pipe | 1,724 / 2,196 / 8,863 | shm > mq > pipe |
| 256KB | 216.0 / 107.3 / 84.3 | shm < mq < pipe | 1,529 / 2,209 / 12,809 | shm > mq > pipe |
| 1MB | 1,085.8 / 393.4 / 461.8 | mq ≈ shm < pipe | 1,242 / 1,858 / 8,879 | shm > mq > pipe |

- 메시지 하나의 컨텍스트 스위치는 pipe 7(64KB) → 19(256KB) → 66.8(1MB), mq 7.1 → 17.4 → 48.8이고, shm은 크기와 관계없이 3이다.
- 1MB 메시지 하나의 CPU 시간(클라이언트 + 서버)은 pipe 1,008.7µs, mq 817.1µs, shm 457.8µs다.

### 클라이언트 수

- 큰 메시지에서는 클라이언트가 늘수록 shm과 나머지의 차이가 벌어진다. 1MB·클라이언트 8의 지연 중앙값은 shm 1,588µs, mq 5,956µs, pipe 10,401µs다.
- 작은 메시지에서는 반대로 shm이 가장 느려진다. 64B·클라이언트 8의 지연 중앙값은 mq 21.66µs, pipe 27.94µs, shm 37.74µs(`mq < pipe < shm`)이고, 처리량도 shm이 13.6MB/s로 가장 낮다.

### pipe의 긴 꼬리

- 처리량 실행(동시 요청 16)에서 pipe와 upipe만 최대 지연이 상위 99%의 수백~수천 배로 튄다. 64KB 이상에서 클라이언트가 2개 이상이면 늘 217배 이상이다(64KB·클라이언트 8은 pipe 1,521배). 클라이언트 8이면 64KB 이상 세 크기의 실행 15번 가운데 pipe는 15번, upipe는 14번에서 평균이 상위 99%보다 크다. 1%도 안 되는 요청이 0.16~1.1초를 기다려 평균을 끌어올린 것이다.
- 같은 조건의 mq와 shm은 1.0~4.8배다. pipe도 클라이언트가 1개면 4.4배 이하이고, 요청(머리 24B + payload)이 `PIPE_BUF`(4096B) 이하인 1KB 이하에서는 3.1배 이하다. 요청이 `PIPE_BUF`를 넘기 시작하는 4KB(4120B)는 클라이언트 2에서 33~46배, 16KB는 클라이언트 2에서만 수백 배로 튄다.

### FIFO와 익명 pipe

- 클라이언트 1에서 익명 pipe(upipe)와 FIFO의 지연 비율은 0.82~1.27로 방향이 일정하지 않고, 처리량과 긴 꼬리도 같은 모양이다. 이름 있는 FIFO를 쓰는 것 자체는 송수신 비용에 차이를 만들지 않았다. 2단계를 FIFO로 구현해도 pipe의 성능을 다르게 재는 것은 아니라는 근거다.

### 측정 비용

- `clock_gettime` 한 번의 비용은 15ns(실행 5번 15~18ns)다. 요청 하나에 보내기 직전과 받은 직후 두 번 부르므로 약 30ns로, 가장 짧은 왕복(약 8µs)의 0.4%다. 작은 메시지의 지연에 섞이는 측정 비용은 무시할 수 있다.

## 해석

잰 사실과, 그 사실을 설명하는 가설을 나눠 적는다. 가설은 T5에서 조건 하나만 바꾸는 실험으로 확인하기 전까지 결론으로 쓰지 않는다.

| 관찰 | 설명 (근거) | 상태와 확인할 실험 |
| --- | --- | --- |
| 16KB 이하에서 세 IPC가 구분되지 않는다 | 복사할 양이 작아 시스템 호출과 깨우기 같은 메시지당 고정 비용이 지배한다. 네 IPC 모두 왕복마다 3번 잠들고 깨며 CPU 시간도 비슷하다 | 근거는 1단계 원자료. 실행 사이 흔들림은 P코어·E코어 배치 때문이라는 가설 → `taskset`으로 P코어(CPU 0~3)만, E코어(CPU 4~11)만 쓰게 해 편차가 줄어드는지 |
| pipe의 컨텍스트 스위치가 크기에 비례한다 | pipe 버퍼(64KB, `F_GETPIPE_SZ`로 확인)가 차면 쓰는 쪽이 잠들고 읽는 쪽이 비우면 깨어, 버퍼 하나를 넘길 때마다 양쪽이 한 번씩 잠든다. 3 + 4 × (크기 / 64KB)가 64KB 7, 256KB 19, 1MB 67로 측정값(7, 19, 66.8)과 맞는다 | 측정값과 맞는 설명. 큰 메시지에서 pipe가 느린 주된 이유로 본다 |
| mq는 1MB를 조각 258개(한 방향 129개, 조각 8184B)로 나르는데 컨텍스트 스위치는 48.8번이다 | 큐(16384B)가 조각 2개만 담아도, 보내는 쪽과 받는 쪽이 서로 다른 코어에서 함께 돌아 조각마다 잠들지 않는다. 그래서 복사가 겹쳐 1MB 지연이 shm과 비슷하다 | 가설 → 모든 프로세스를 CPU 하나에 묶어(`taskset -c`) mq의 컨텍스트 스위치가 조각 수 가까이 늘고 1MB 지연이 shm보다 길어지는지 |
| shm의 1MB 지연은 mq보다 짧지 않은데 처리량은 4.8배다 | shm은 메시지 전체를 링에 복사한 뒤에 알리므로 한 메시지 안에서는 복사가 겹치지 않는다(지연). 대신 커널을 거치지 않는 복사라 메시지당 CPU 시간이 mq의 절반 정도이고, 요청을 쌓아 보내면 차이가 처리량으로 드러난다 | 가설 → 위 실험에서 shm의 지연은 거의 그대로인지, `perf stat`으로 메시지당 커널 시간 비교 |
| 작은 메시지·클라이언트 8에서 shm이 가장 느리다 | 요청 링 하나를 클라이언트 8개가 `semop`(MUTEX, 빈 칸, `SEM_UNDO`)으로 다투고, 메시지마다 `semop`이 보내는 쪽 2번·받는 쪽 2번 든다 | 가설 → 클라이언트 수만 바꿔 메시지당 CPU 시간과 비자발적 컨텍스트 스위치를 비교, 2단계에서 세마포어 대기 시간을 구간별로 잰다 |
| pipe의 긴 꼬리 | `PIPE_BUF`보다 큰 요청은 여러 번 나눠 쓰므로 요청 FIFO를 `fcntl` 잠금(`/tmp/osproject_2_req.lock`)으로 독점한다. 이 잠금은 먼저 기다린 순서를 보장하지 않아, 잠금을 놓자마자 다시 잡는 클라이언트 때문에 한 클라이언트가 오래 굶을 수 있다. 꼬리가 pipe·upipe에서만, 요청이 `PIPE_BUF`를 넘는 4KB 이상에서만, 클라이언트가 2개 이상일 때만 나타나는 것과 맞는다 | 가설 → 요청마다 잠금을 기다린 시간을 기록하거나, 잠금 대신 클라이언트별 요청 FIFO를 쓰는 옵션을 만들어 꼬리가 사라지는지 |

## 2단계 예측에 쓸 때

- 응용의 요청은 모두 `PIPE_BUF` 이하이고 응답만 1MB + 32B까지 커진다([설계 명세](../design/README.md#채널)). 요청 쪽은 이 문서의 16KB 이하 결과, 응답 쪽은 64KB 이상 결과가 해당한다.
- pipe의 긴 꼬리는 `PIPE_BUF`를 넘는 요청에서만 생겼다. 위 가설이 맞으면 요청이 작은 응용에는 나타나지 않는다.
- 16KB 이하의 차이는 실행 사이 흔들림보다 작다. 작은 요청의 순위를 1단계 값만으로 예측하지 않는다.
