## 결과

반복 20번 측정(`results/stage1-r20/`)의 값이다.

### 16KB 이하: 지연으로는 세 IPC가 구분되지 않는다

- 클라이언트 1의 왕복 지연 중앙값은 64B~16KB에서 pipe 9.93~21.12µs, mq 8.10~16.75µs, shm 9.57~16.02µs다. 실행 사이 편차((최대 − 최소) / 중앙값)가 54~124%로 IPC 사이의 차이보다 커서 순위는 모두 `pipe ≈ mq ≈ shm`이다.
- 처리량(동시 요청 16)은 mq가 가장 높다. 64B에서 mq 47.5MB/s, shm 32.8MB/s, pipe 28.3MB/s(`mq > shm > pipe`), 4KB에서 `mq ≈ shm > pipe`다.
- 메시지 하나의 자발적 컨텍스트 스위치(클라이언트 + 서버)는 세 IPC 모두 3번이고, 64B의 CPU 시간은 11.3~13.6µs로 비슷하다.

### 64KB 이상: pipe가 가장 느리고, 처리량은 shm이 크게 앞선다

| 크기 | 지연 중앙값 pipe / mq / shm (µs) | 지연 순위 | 처리량 pipe / mq / shm (MB/s) | 처리량 순위 |
| --- | --- | --- | --- | --- |
| 64KB | 82.3 / 34.7 / 34.4 | mq ≈ shm < pipe | 1,485 / 2,104 / 9,221 | shm > mq > pipe |
| 256KB | 273.5 / 108.1 / 91.9 | shm < mq < pipe | 1,255 / 2,202 / 12,131 | shm > mq > pipe |
| 1MB | 1,159.0 / 393.9 / 422.6 | mq ≈ shm < pipe | 1,069 / 1,862 / 9,388 | shm > mq > pipe |

- 메시지 하나의 컨텍스트 스위치는 pipe 7.0(64KB) → 19.0(256KB) → 66.8(1MB), mq 7.5 → 17.6 → 41.0이고, shm은 크기와 관계없이 3이다.
- 1MB 메시지 하나의 CPU 시간(클라이언트 + 서버)은 pipe 1,114.6µs, mq 762.5µs, shm 447.1µs다.

### 클라이언트 수

- 큰 메시지에서는 클라이언트가 늘수록 shm과 나머지의 차이가 벌어진다. 1MB·클라이언트 8의 지연 중앙값은 shm 1,735µs, mq 6,148µs, pipe 10,233µs다.
- 작은 메시지에서는 반대로 shm이 가장 느려진다. 64B·클라이언트 8의 지연 중앙값은 mq 23.09µs, pipe 26.84µs, shm 38.10µs(`pipe ≈ mq < shm`)이고, 처리량도 shm이 14.9MB/s로 가장 낮다.

### pipe의 긴 꼬리

- 처리량 실행(동시 요청 16)에서 pipe와 upipe만 최대 지연이 상위 99%의 수백~수천 배로 튄다. 64KB 이상에서 클라이언트가 2개 이상이면 205~1,613배이고, 클라이언트 8이면 64KB 이상 세 크기의 실행 60번 가운데 pipe는 54번, upipe는 56번에서 평균이 상위 99%보다 크다. 1%도 안 되는 요청이 아주 오래 기다려 평균을 끌어올린 것이다.
- 같은 조건의 mq와 shm은 1.0~3.6배다. pipe도 클라이언트가 1개면 3.8배 이하이고, 요청(머리 24B + payload)이 `PIPE_BUF`(4096B) 이하인 1KB 이하에서는 클라이언트 수와 관계없이 3.7배 이하다. 요청이 `PIPE_BUF`를 넘기 시작하는 4KB(4120B)는 클라이언트 2에서 27~40배, 16KB는 클라이언트 2에서만 수백 배로 튄다. 처음 측정과 같은 모양이다.

### FIFO와 익명 pipe

- 클라이언트 1에서 익명 pipe(upipe)와 FIFO의 지연 비율은 0.90~1.03이고 긴 꼬리도 같은 모양이다. 이름 있는 FIFO를 쓰는 것 자체는 송수신 비용에 차이를 만들지 않았다. 2단계를 FIFO로 구현해도 pipe의 성능을 다르게 재는 것은 아니라는 근거다.

### 측정 비용

- `clock_gettime` 한 번의 비용은 23ns(실행 20번의 중앙값)다. 요청 하나에 보내기 직전과 받은 직후 두 번 부르므로 약 46ns로, 가장 짧은 왕복(약 8µs)의 0.6%다. 작은 메시지의 지연에 섞이는 측정 비용은 무시할 수 있다.

## 원인 확인 실험

결과를 설명하는 가설마다 CPU 배치나 IPC 한도 하나만 바꿔 쟀다(`scripts/exp-stage1.sh`, 반복 20번, 클라이언트 1). 비교 표는 [1단계 실험 비교](../assets/bench/experiments.md)에 있다. 실험한 날과 코드는 반복 20번 측정과 같다(`pbig`만 실험 스크립트를 고친 뒤인 `cbebff6`, 측정 코드는 같다).

| 실험 | 바꾼 것 (기준 → 실험) | 결과 원자료 |
| --- | --- | --- |
| `pcore`, `ecore` | CPU 배치: 전체 12개 → P코어(CPU 0~3)만 / E코어(CPU 4~11)만. 64B·4KB | `results/exp-pcore/`, `results/exp-ecore/` |
| `pbig` | CPU 배치: 전체 → P코어만. 64KB·1MB | `results/exp-pbig/` |
| `cpu1` | CPU 배치: P코어 4개(`pbig`) → 논리 CPU 하나(2번). 64KB·1MB | `results/exp-cpu1/` |
| `msgmax-up` | mq 한도: `msgmax` 8192·`msgmnb` 16384 → 1048640·16777216 (1MB 메시지를 조각 하나로). mq만, 전체 조합 | `results/exp-msgmax-up/` |

### 작은 메시지의 흔들림은 P코어·E코어 배치 때문이다 (확인)

- P코어에만 두면 64B·4KB의 지연 중앙값이 절반 가까이로 줄고(64B pipe 9.93 → 4.99µs, mq 8.36 → 4.40µs, shm 9.57 → 5.38µs), 실행 사이 편차도 59~92%에서 8~28%로 줄었다.
- E코어에만 두면 지연은 기준과 비슷하고(64B pipe 9.97µs, mq 8.78µs, shm 11.29µs) 편차는 21~56%다.
- 기준의 지연이 E코어 값에 가깝고, 실행마다 P코어에 얼마나 놓이느냐에 따라 값이 흔들린 것이다. 16KB 이하의 순위를 매기지 못한 것은 IPC의 차이가 이 흔들림에 묻혔기 때문이다.

### mq는 다른 코어에서 조각 송수신을 겹친다 (확인)

- P코어 4개(`pbig`)에서 CPU 하나(`cpu1`)로 바꾸면 mq의 1MB 메시지당 컨텍스트 스위치가 31.3번에서 253.2번으로 늘어 조각 수(왕복 258개)에 가까워지고, 지연은 389.5µs에서 840.6µs로 2.2배가 된다.
- 같은 변화에서 shm의 1MB 지연은 185.3µs에서 193.5µs로 거의 그대로다. shm은 메시지 전체를 링에 복사한 뒤 알리므로 원래 겹칠 것이 없다.
- 따라서 CPU가 여럿이면 mq의 보내는 쪽과 받는 쪽이 서로 다른 코어에서 함께 돌아 조각마다 잠들지 않는다. AI가 설명한 "조각마다 송수신이 교대한다"는 CPU 하나일 때만 맞다([AI 활용 기록](../records/ai-log.md)의 틀린 사례 4번).
- pipe는 CPU 하나에서 오히려 빨라졌다(1MB 477.9 → 286.9µs, 컨텍스트 스위치 67.0 → 35.4번). 다른 코어의 상대를 깨우는 비용이 같은 CPU에서 번갈아 도는 비용보다 크다는 뜻으로 보이지만, 이 실험만으로는 원인을 나누지 못했다.

### 묶지 않은 1MB에서 mq와 shm이 비슷한 것은 두 효과가 겹친 결과다

- P코어에만 두면 1MB 지연이 shm 185.3µs, mq 389.5µs로 shm이 절반이다. 묶지 않으면 shm은 422.6µs로 크게 느려지고 mq는 393.9µs로 거의 그대로다.
- shm은 1MB를 한 번에 복사하므로 그 복사가 E코어에 놓이면 그대로 느려지고, mq는 조각 복사를 여러 코어에 나눠 겹쳐 E코어의 영향을 덜 받는다. 그래서 묶지 않은 측정에서만 `mq ≈ shm`이 된다.

### mq 한도를 올리면 처리량은 늘고 단일 요청 지연은 나빠진다

| 크기 | 지연 중앙값 기본 → 상향 (µs) | 처리량 기본 → 상향 (MB/s) | 컨텍스트 스위치 기본 → 상향 | 클라이언트 8 지연 기본 → 상향 (µs) |
| --- | --- | --- | --- | --- |
| 64KB | 34.7 → 66.2 | 2,104 → 4,417 | 7.5 → 3.0 | 368.6 → 98.6 |
| 256KB | 108.1 → 206.8 | 2,202 → 4,752 | 17.6 → 3.0 | 1,419.8 → 468.6 |
| 1MB | 393.9 → 1,359.4 | 1,862 → 2,791 | 41.0 → 3.0 | 6,148.3 → 4,036.7 |

- 조각이 하나가 되면 메시지당 잠드는 횟수가 shm과 같은 3번으로 줄어, 처리량이 64KB·256KB에서 2배 넘게, 1MB에서 1.5배로 늘고 클라이언트가 많을 때의 지연도 줄었다.
- 대신 조각 송수신을 겹치지 못해 클라이언트 1의 지연은 64KB·256KB에서 약 2배, 1MB에서 3.5배로 늘었다. 1MB 상향의 지연은 shm(422.6µs)보다 세 배 넘게 길다.
- 4KB 이하는 기본 한도에서도 조각 하나라 지연이 비슷하다(64B 8.4 → 7.5µs, 4KB 10.7 → 12.7µs).

## 해석

| 관찰 | 설명 (근거) | 상태 |
| --- | --- | --- |
| 16KB 이하에서 세 IPC가 지연으로 구분되지 않는다 | 복사할 양이 작아 시스템 호출과 깨우기 같은 메시지당 고정 비용이 지배한다. 세 IPC 모두 왕복마다 3번 잠들고 깨며 CPU 시간도 비슷하다. 그 위에 P코어·E코어 배치의 흔들림이 차이를 덮는다 | 확인(`pcore`, `ecore`) |
| pipe의 컨텍스트 스위치가 크기에 비례한다 | pipe 버퍼(64KB, `F_GETPIPE_SZ`로 확인)가 차면 쓰는 쪽이 잠들고 읽는 쪽이 비우면 깨어, 버퍼 하나를 넘길 때마다 양쪽이 한 번씩 잠든다. 3 + 4 × (크기 / 64KB)가 64KB 7, 256KB 19, 1MB 67로 측정값(7.0, 19.0, 66.8)과 맞는다 | 측정값과 맞는 설명. P코어에만 두어도 67.0번으로 같다 |
| mq는 조각 258개를 41번 잠들고 나른다 | 보내는 쪽과 받는 쪽이 다른 코어에서 함께 돌아 조각 송수신이 겹친다 | 확인(`cpu1`) |
| 1MB에서 `mq ≈ shm` | mq의 겹치기와 shm의 E코어 영향이 겹친 결과다. P코어에만 두면 shm이 mq의 절반이다 | 확인(`pbig`, `cpu1`) |
| shm의 처리량이 크게 앞선다 | 커널을 거치지 않고 링에 한 번 복사하고, 메시지당 잠드는 횟수가 3번으로 일정하다. 메시지당 CPU 시간이 1MB에서 mq의 0.59배, pipe의 0.40배다 | 근거는 원자료. 복사 위치별 시간은 재지 않았다 |
| 작은 메시지·클라이언트 8에서 shm이 가장 느리다 | 요청 링 하나를 클라이언트 8개가 `semop`(MUTEX, 빈 칸, `SEM_UNDO`)으로 다투고, 메시지마다 `semop`이 보내는 쪽 2번·받는 쪽 2번 든다 | 가설. 2단계 구간별 시간에서 세마포어 대기를 잰다 |
| pipe의 긴 꼬리 | `PIPE_BUF`보다 큰 요청은 요청 FIFO를 `fcntl` 잠금(`/tmp/osproject_2_req.lock`)으로 독점하는데, 이 잠금은 먼저 기다린 순서를 보장하지 않아 한 클라이언트가 오래 굶을 수 있다. 꼬리가 pipe·upipe에서만, 요청이 `PIPE_BUF`를 넘는 크기에서만, 클라이언트가 2개 이상일 때만 나타나는 것과 맞는다 | 가설. 확인하려면 전송 계층 코드를 바꿔야 한다(요청마다 잠금 대기 시간 기록, 또는 클라이언트별 요청 FIFO 옵션) |

## 2단계와 예측에 쓸 때

- 응용의 요청은 모두 `PIPE_BUF` 이하이고 응답만 1MB + 32B까지 커진다([설계 명세](../design/README.md#채널)). 요청 쪽은 16KB 이하 결과, 응답 쪽은 64KB 이상 결과가 해당한다.
- pipe의 긴 꼬리는 `PIPE_BUF`를 넘는 요청에서만 생겼다. 위 가설이 맞으면 요청이 작은 응용에는 나타나지 않는다.
- 16KB 이하의 차이는 CPU 배치의 흔들림보다 작다. 2단계도 CPU를 묶지 않고 재므로, 작은 요청의 순위를 1단계 값만으로 예측하지 않는다.
- mq 한도는 기본값으로 잰다([구현 계획의 미결정](../design/plan.md#리스크-및-미결정)). 상향은 처리량과 다중 클라이언트 지연을 개선하지만 단일 요청 지연을 늘리는 맞바꿈이라, 기본값 결과에 이 실험을 함께 보고한다.
