# 요구사항 — 다중 그림판 공유 캔버스 서버

[문서 안내](../../README.md#관련-문서)

보고서 1장(문제 정의, 요구사항 분석)의 원본이다. 과제가 요구하는 조건과 배점의 원본은 [과제 핵심 정리](../assignment/README.md)이고, 이 문서는 우리 응용이 무엇을 해야 하는지만 정한다.

## 문제 정의

여러 사람이 한 컴퓨터 안에서 같은 그림판에 동시에 그리는 **협업 그림판 서버**다. 서버는 그림판(방) 여러 개를 메모리에 두고, 많은 클라이언트가 동시에

1. 작은 그리기 명령(DRAW, 요청 40B)을 아주 자주 보내고,
2. 자기가 보는 영역의 그림(SNAPSHOT, 응답 최대 64KB)을 주기적으로 받아 간다.

같은 응용을 pipe(FIFO), message queue, shared memory 3가지 IPC로 만들어, **어떤 IPC가 어떤 조건에서 유리한지**를 1단계 측정으로 예측하고 2단계 측정으로 검증한다.

### 왜 IPC 선택이 성능을 좌우하는가

이 응용의 통신은 1단계에서 IPC 순위가 서로 다르게 나온 세 영역에 동시에 걸쳐 있다.

| 통신 | 크기·빈도 | 1단계에서 본 것 |
| --- | --- | --- |
| DRAW 요청·응답 | 40B·56B, 요청의 90% | 16KB 이하는 세 IPC의 지연이 구분되지 않았다. 메시지당 고정 비용(시스템 호출, 깨우기)이 지배한다 |
| SNAPSHOT 응답 | 64KB, 요청의 10%지만 응답 바이트의 99% | 64KB 이상에서 pipe가 가장 느리고 shm의 처리량이 4배 이상 앞섰다. 복사·잠듦 횟수가 지배한다 |
| 클라이언트 수 | 최대 1024개가 요청 채널 하나를 함께 쓴다 | 클라이언트 8개, 작은 메시지에서 shm이 가장 느렸다. 채널 구조와 경쟁이 지배한다 |

그래서 클라이언트 수와 요청 종류에 따라 가장 좋은 IPC가 바뀔 수 있고, 이를 측정으로 확인하는 것이 이 과제의 목표다.

### 설계과제 목표

- 1단계 측정을 근거로 워크로드별 IPC 성능을 구현 전에 예측한다([성능 예측](../records/prediction.md)).
- 같은 응용을 세 IPC로 구현하고, 경쟁 상태와 교착 없이 클라이언트 1024개까지 동작시킨다.
- 같은 컴퓨터에서 세 버전을 재서 예측과 비교하고, 틀린 부분의 원인을 요인 하나만 바꾼 실험으로 확인한다.
- 측정 결과로 설계를 1번 이상 개선하고 전후를 비교한다. 마지막에 우리 응용의 IPC 선택 기준을 정리한다.

## 범위

- 포함: 그림판 여러 개, 사각형 그리기(DRAW), 영역 조회(SNAPSHOT), 통계(STATS), 3가지 IPC 버전, 자동 그리기 클라이언트, 사람이 마우스로 그리는 그리기 클라이언트, 클라이언트 N개를 함께 띄우는 실행기, 정답 검증기, 1단계 echo 벤치마크.
- 제외: 네트워크 통신, 창(GUI) 프로그램(그리기 클라이언트는 터미널에 그린다), 선·글자 그리기, 1바이트 밖의 색, 편집 충돌 해결, 영속 저장(종료 때 그림판 0을 PGM으로 한 번 저장할 뿐이다).

### 용어

| 용어 | 뜻 |
| --- | --- |
| 그림판(방) | 서버가 가진 1024 × 1024칸 배열. 한 칸은 0~255의 값 하나다(1MB). 서버는 K개를 둔다 |
| 타일 | 그림판을 정사각형으로 나눈 구역. 락의 단위다(기본 64 × 64칸, 그림판 하나에 256개) |
| DRAW, SNAPSHOT | 사각형 영역의 값에 v 더하기, 영역 내용 받기 |
| 자동 그리기 클라이언트 | 시드로 정해진 요청열대로 쉬지 않고 그리고(DRAW) 보는(SNAPSHOT) 클라이언트(`client_<ipc>`). 측정과 데모에 쓴다 |
| 그리기 클라이언트 | 사람이 터미널에서 마우스로 그리는 클라이언트(`draw_<ipc>`) |
| 실행기 | 자동 그리기 클라이언트 N개를 띄우고 측정 시작을 맞추는 프로그램(`loadgen`) |
| 전송 계층 | `include/transport.h`를 구현한 IPC별 코드. 세 버전의 유일한 차이다 |
| 요청 채널, 응답 채널 | 클라이언트에서 서버로, 서버에서 클라이언트로 가는 통로 |
| 왕복 지연 | 요청을 보내기 직전부터 응답을 다 받은 직후까지의 시간 |
| 처리량 | 서버 전체가 초당 처리한 요청 수(req/s)와 응답 바이트 수(MB/s) |
| 구간별 시간 | 왕복 지연을 요청 전송·큐 대기·락 대기·처리·응답 전송으로 나눈 값 |
| 체크섬 | 그림판 내용으로 계산한 값. 서버 결과와 검증기 정답이 같은지 비교한다 |
| 측정용 컴퓨터 | 모든 수치를 재는 컴퓨터 1대(이동건 PC, [측정 방법](../measurement/README.md#측정용-컴퓨터)) |

## 기능 요구사항

| 번호 | 요구사항 |
| --- | --- |
| F-1 | 서버는 그림판 K개(1~64, 서버 옵션)를 둔다. 그림판 하나는 1024 × 1024칸, 칸당 1바이트이고 처음에는 모두 0이다. |
| F-2 | DRAW(방, x, y, w, h, v)는 사각형 안의 모든 칸에 v를 더한다(mod 256). 다른 요청이 DRAW 하나를 반쯤 반영된 상태로 보지 않는다. 더하기는 순서와 무관하므로, 같은 DRAW 묶음이면 처리 순서와 관계없이 결과가 같다. |
| F-3 | SNAPSHOT(방, x, y, w, h)은 영역(한 변 1~256칸, 최대 64KB)의 내용을 응답으로 보낸다. 영역 전체가 한 시점의 내용이다. 더 넓은 영역은 여러 번 나눠 요청한다. |
| F-4 | STATS는 서버의 처리 건수(DRAW, SNAPSHOT, 오류), 접속한 클라이언트 수, 그림판 수, 워커 수를 돌려준다. |
| F-5 | 클라이언트는 번호(0~1023)로 접속(HELLO)하고 끝낼 때 BYE를 보낸다. 같은 번호가 실행 중이면 새 클라이언트를 거부한다. |
| F-6 | 방 번호가 범위를 벗어나거나, 영역이 그림판을 벗어나거나, 크기가 0이거나, SNAPSHOT 한 변이 256을 넘는 요청에는 오류로 응답하고 그림판을 바꾸지 않는다. |
| F-7 | 모든 응답 앞에 서버 시각 4개(받음, 큐에서 꺼냄, 락 획득, 응답 직전)를 붙여 클라이언트가 구간별 시간을 계산할 수 있게 한다. |
| F-8 | 서버는 SIGINT·SIGTERM을 받으면 새 요청을 멈추고, 받은 요청을 끝까지 처리한 뒤 그림판별 체크섬을 출력하고 그림판 0을 PGM으로 저장하고 IPC 자원을 모두 지운다. 두 번째 신호를 받으면 기다리지 않고 자원만 지우고 끝낸다. |
| F-9 | 자동 그리기 클라이언트는 시드로 정해진 요청열([워크로드 명세](../records/prediction.md#워크로드-명세))을 개수(`-n`) 또는 시간(`-d`)만큼 보내고, 지연(평균·중앙값·상위 99%·최대, 요청 종류별), 처리량, CPU 시간, 컨텍스트 스위치, 메모리를 출력하고 CSV에 남긴다. 동시에 띄워 둘 요청 수(`-f`)로 지연과 처리량을 나눠 잰다. |
| F-10 | 그리기 클라이언트는 사람이 터미널에서 마우스로 그림판에 그리고, 같은 그림판에 다른 클라이언트가 그린 것을 주기적으로 받아 보여 준다. 색·붓 크기·확대·이동을 바꿀 수 있고, 상태 줄에 접속 수와 왕복 지연을 보여 준다. |
| F-11 | 검증기는 자동 그리기 클라이언트들의 시드와 보낸 요청 수로 요청열을 다시 만들어 스레드 하나로 그리고, 그림판별 정답 체크섬을 서버와 같은 형식으로 출력한다. |
| F-12 | 실행기는 자동 그리기 클라이언트 N개(1~1024)를 띄워 그림판에 나눠 배치하고, 모두 워밍업을 마치면 측정을 함께 시작시키고, 모두 끝나면 클라이언트 결과를 모아 한 실행의 지연 분포(모든 요청의 표본을 합친 백분위수)와 처리량을 낸다. |

## 비기능 요구사항

| 번호 | 요구사항 |
| --- | --- |
| N-1 | 규모: 세 버전 모두 클라이언트 1024개, 그림판 64개까지 동작한다. |
| N-2 | 목표 성능: 사람 1024명이 동시에 그리는 부하(사람 1명 = DRAW 60회/s + SNAPSHOT 약 6.7회/s, 합계 약 68,000 요청/s, 응답 약 448MB/s)를 감당하고, 이때 DRAW 왕복 지연 상위 99%가 16.7ms(60Hz 화면 한 프레임) 이하다. 자동 그리기 클라이언트는 쉬지 않고 보내므로, 측정한 최대 처리량이 이 목표를 넘는지로 판정한다. |
| N-3 | 경쟁 상태와 교착이 없다. 어떤 IPC·락 방식·클라이언트 수에서도 서버 체크섬이 검증기 정답과 같고, ThreadSanitizer 빌드의 보고가 0건이다. 락을 여러 개 잡을 때는 정한 순서로만 잡는다. |
| N-4 | 정상 종료 뒤 `ipcs`와 `/tmp`에 우리 자원(key 60020~60029, `/tmp/osproject_2_*`)이 남지 않는다. 비정상 종료(`kill -9`)로 남은 자원은 다음 서버나 `make ipcclean`이 지운다. |
| N-5 | 메모리 사용량을 줄이는 방안을 1개 이상 설계에 넣고 효과를 VmRSS로 확인한다. IPC 버퍼는 클라이언트 하나에 160KB 이하로 잡는다(1024개면 160MB 이하). |
| N-6 | 성능을 높이는 방안을 1개 이상 측정으로 찾고 전후를 비교한다. |
| N-7 | 측정 구간 안에서 출력(`printf` 등)과 `malloc`을 하지 않는다. |

## 실행 환경과 제약

| 번호 | 제약 |
| --- | --- |
| C-1 | Linux, C(gnu11), gcc, POSIX·System V API만 쓴다. 외부 라이브러리를 쓰지 않는다. 채점 환경인 Ubuntu + gcc에서 `make`로 빌드된다. |
| C-2 | 서버와 모든 클라이언트는 프로세스마다 스레드를 3개 이상 쓴다. |
| C-3 | 클라이언트를 2개 이상 동시에 실행할 수 있다(최대 1024개). |
| C-4 | `make`를 쓴다. 1단계 벤치마크와 2단계 각 버전을 따로 빌드할 수 있고(`make pipe` 등), `make` 한 번으로 전체를 빌드한다. |
| C-5 | System V key는 60020~60029(60xxy, 2팀), 파일 이름은 `/tmp/osproject_2_*`만 쓴다. key 없는 자원(`IPC_PRIVATE`)은 우리 이름의 파일에 기록해 정리할 수 있게 한다. |
| C-6 | 만든 IPC 자원은 모든 종료 경로에서 지운다. 실행 뒤 `ipcs` 결과를 보고서에 넣는다. |
| C-7 | 세 버전은 같은 응용이다. 응용 로직(그림판, 서버, 클라이언트)은 공통 모듈이고 IPC 고유 호출은 전송 계층에만 있다. |
| C-8 | 모든 측정은 측정용 컴퓨터 1대에서 `clock_gettime(CLOCK_MONOTONIC)`으로 재고, 워밍업 뒤 조건마다 30번 이상 반복한다. 원자료(CSV)와 스크립트를 제출물에 넣는다. |
| C-9 | 락 방식, 워커 수, 그림판 수 같은 설계 선택과 개선 전후는 실행 옵션으로 바꾼다. 실험마다 코드를 고쳐 다시 빌드하지 않는다. |
| C-10 | 성능 예측은 서버·클라이언트를 구현하기 전에 커밋하고, 이후에는 고치지 않고 수정 기록만 덧붙인다. |

## 완료 기준

- `make test`의 FAIL이 0이다([테스트 명세](../verification/README.md)). SKIP은 완료가 아니다.
- 1단계 결과로 쓴 예측이 구현보다 먼저 커밋되어 있다(git 기록).
- 같은 컴퓨터에서 세 버전을 조건마다 30번 이상 재서 원자료가 `results/`에 있고, 예측 대비 비교·원인 확인 실험·설계 개선 전후 비교가 [2단계 측정 결과](../measurement/stage2.md)에 있다.
- 최종보고서, 발표자료, 발표 대본, 데모 영상, 제출 tar가 있다([제출 준비](../submission/README.md)).
