# 요구사항 — 공유 캔버스 서버

[문서 안내](../../README.md#관련-문서)

## 개요

공유 캔버스 서버: 여러 클라이언트가 하나의 캔버스에 동시에 그리고, 캔버스의 일부나 전체를 받아 가는 서버다. 같은 응용을 pipe, message queue, shared memory 3버전으로 만들어 성능을 비교한다. 작은 그리기 명령(수십 B)과 큰 화면 데이터(최대 1MB)가 섞인 통신에서 어떤 IPC가 언제 유리한지 측정으로 답하는 것이 목적이다.

과제가 요구하는 조건과 배점의 원본은 [과제 핵심 정리](../assignment/README.md)다. 이 문서는 우리 응용이 무엇을 해야 하는지만 정한다. 보고서 1.2절은 이 문서에서 옮긴다.

## 범위

- 포함: 사각형 그리기, 영역 조회, 통계 조회, 1단계 echo 벤치마크, 3가지 IPC 버전, 정답 검증기.
- 제외: 네트워크 통신, GUI와 실시간 화면 표시, 선·글자 그리기, 색상(1바이트 회색조만), 편집 충돌 해결, 캔버스 영속 저장(종료 시 1회 저장만).
- 미확정: **뷰어 방송**(서버가 주기적으로 화면을 보내는 1:N 통신). 대기 이유는 팀 결정 전이기 때문이다. 11월 15일까지 넣기로 정하면 이 문서에 F-11로 추가한 뒤 예측을 쓴다. 정하지 못하면 넣지 않는다.

### 용어

| 용어 | 뜻 |
| --- | --- |
| 캔버스 | 서버가 가진 1024 × 1024칸 배열. 한 칸은 0~255의 값 하나다 |
| 타일 | 캔버스를 64 × 64칸으로 나눈 구역. 락의 단위다 |
| DRAW, SNAPSHOT | 사각형 그리기 요청, 영역 조회 요청 |
| 전송 계층 | `transport.h`를 구현한 IPC별 코드. 세 버전의 유일한 차이다 |
| 요청 채널, 응답 채널 | 클라이언트에서 서버로, 서버에서 클라이언트로 가는 통로 |
| 워크로드 | 요청의 종류·크기·비율·빈도를 정한 실험 조건 |
| 왕복 지연 | 요청을 보내기 직전부터 응답을 다 받은 직후까지의 시간 |
| 처리량 | 초당 처리한 메시지 수와 바이트 수 |
| 구간별 시간 | 왕복 지연을 요청 전송·큐 대기·락 대기·처리·응답 전송으로 나눈 값 |
| 체크섬 | 캔버스 전체에서 계산한 값. 두 캔버스가 같은지 비교하는 데 쓴다 |
| 측정용 컴퓨터 | 보고서의 모든 수치를 재는 컴퓨터 1대 |
| 1단계, 2단계 | echo 벤치마크 측정, 팀 응용의 구현과 측정 |

## 실행 환경과 제약

| 번호 | 제약 |
| --- | --- |
| C-1 | Linux, C(gnu11), gcc, POSIX API만 쓴다. 외부 라이브러리를 쓰지 않는다. 채점 환경인 Ubuntu + gcc에서 `make`로 빌드된다. |
| C-2 | 서버와 클라이언트는 프로세스마다 스레드를 3개 이상 쓴다. |
| C-3 | 클라이언트를 2개 이상 동시에 실행할 수 있다. 최대 16개(`MAX_CLIENTS`). |
| C-4 | System V IPC의 key는 60020 ~ 60029(2팀)만 쓴다. FIFO 등 파일은 `/tmp/osproject_2_` 로 시작한다. |
| C-5 | 정상 종료와 SIGINT·SIGTERM 종료 모두에서 만든 IPC 자원과 FIFO를 지운다. |
| C-6 | 응용 로직(서버, 클라이언트, 벤치마크)은 한 벌이다. IPC 버전은 `transport.h` 구현만 다르다. |
| C-7 | Makefile은 벤치마크와 응용의 각 버전을 따로 빌드할 수 있고, `make` 한 번으로 전체를 빌드한다. |
| C-8 | 보고서에 쓰는 모든 수치는 측정용 컴퓨터 1대에서 직접 측정한 값이다. |
| C-9 | 락 방식 같은 설계 선택은 실행 옵션으로 바꾼다. 실험을 위해 코드를 고쳐 다시 빌드하지 않는다. |

## 기능 요구사항

| 번호 | 요구사항 |
| --- | --- |
| F-1 | 서버는 1024 × 1024칸, 한 칸 1바이트(전체 1MB)의 캔버스를 0으로 초기화해 보유한다. |
| F-2 | `DRAW_RECT(x, y, w, h, v)`: 사각형 영역의 각 칸에 v를 더한다(256으로 나눈 나머지). 응답은 확인과 서버 시각이다. |
| F-3 | `SNAPSHOT(x, y, w, h)`: 사각형 영역을 복사해 w × h 바이트로 응답한다. 최대 1MB다. |
| F-4 | `STATS`: 처리한 DRAW·SNAPSHOT 건수, 보낸 바이트 수, 클라이언트 수, 워커 수를 응답한다. |
| F-5 | 영역이 캔버스를 벗어나거나 w, h가 0이면 오류로 응답하고 캔버스를 바꾸지 않는다. |
| F-6 | 모든 응답에는 서버의 수신·큐 꺼냄·락 획득·송신 직전 시각이 실린다. |
| F-7 | 클라이언트는 시드로 정해지는 요청열을 만든다. 같은 시드와 옵션이면 세 버전이 받는 요청열이 같다. |
| F-8 | 클라이언트는 요청마다 왕복 지연과 구간별 시간을 기록하고, 끝날 때 통계를 출력하고 CSV로 저장한다. |
| F-9 | 서버는 종료할 때 캔버스를 PGM 이미지로 저장하고 체크섬을 출력한다. |
| F-10 | 검증기는 같은 시드들의 요청을 스레드 하나로 재생해 정답 체크섬을 출력한다. |
| F-11 | (미확정) 뷰어 방송. [범위](#범위) 참고. |
| F-12 | 1단계 벤치마크는 받은 메시지를 같은 크기로 돌려주는 echo 방식으로, 메시지 크기 5단계 이상과 클라이언트 1·2·4·8개에서 지연과 처리량을 잰다. 응용과 같은 `transport.h` 구현을 쓴다. |

## 비기능 요구사항

| 번호 | 요구사항 |
| --- | --- |
| N-1 | 정합성: 락을 켠 상태에서는 어떤 실행 순서에서도 최종 체크섬이 정답과 같다. |
| N-2 | 교착 없음: 클라이언트 8개, 워커 여러 개로 돌려도 멈추지 않고 끝난다. |
| N-3 | 섞임 없음: 같은 클라이언트로 가는 두 응답의 바이트가 섞이지 않는다. |
| N-4 | 측정 가능: 지연(평균, 중앙값, 상위 99%, 최대), 처리량, CPU 시간, 컨텍스트 스위치, VmRSS를 버전마다 같은 방법으로 잰다. |
| N-5 | 메모리: 사용량을 줄이는 방안을 1개 이상 넣고 VmRSS로 효과를 확인한다. |
| N-6 | 목표 지연과 처리량: 미확정. 1단계 측정 뒤 [성능 예측](../records/prediction.md)에 수치로 정한다. 측정 전에 임의의 목표값을 쓰지 않는다. |

## 출력과 오류 처리

- 측정 구간 안에서는 화면에 출력하지 않는다. 통계와 체크섬은 실행이 끝난 뒤 stdout에 쓴다.
- 안내와 오류는 stderr에 한 줄로 쓰고, 실패하면 종료 코드 1로 끝난다.
- 서버를 찾지 못한 클라이언트, 이미 떠 있는 서버 위에 또 띄운 서버는 이유를 알리고 끝난다. 남의 자원을 지우지 않는다.
- CSV의 열은 [측정 방법](../measurement/README.md#원자료-형식)을 따른다.

## 완료 기준

[테스트 명세](../verification/README.md)의 항목으로 확인한다. 아래는 수용 조건이며 검증 완료 기록이 아니다.

1. `make`가 경고 없이 통과하고, `make pipe`, `make mq`, `make shm`, `make bench`, `make app`이 각각 동작한다.
2. 세 버전 모두 클라이언트 2개 이상 동시 실행에서 체크섬이 정답과 일치한다.
3. 락을 끄면 체크섬이 어긋나는 것을 보일 수 있다.
4. 정상 종료와 Ctrl+C 종료 뒤 `ipcs`와 `/tmp`에 우리 자원이 남지 않는다.
5. 1단계와 2단계의 측정 스크립트를 다시 돌리면 `results/`의 원자료와 같은 형식의 결과가 나온다.
