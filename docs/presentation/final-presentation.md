# 최종 발표 준비 기준 — 공유 캔버스 서버

[문서 안내](../../README.md#관련-문서)

발표자료(PPT)와 발표 동영상의 구성, 데모 장면, 점검을 담당한다. 구성의 원본은 [최종보고서 서식](../assignment/UNIX시스템프로그래밍_설계과제_최종보고서서식.docx)의 별첨이다. 각 쪽에 넣을 근거는 [보고서 절별 출처](final-report.md#보고서-절별-출처)에서 가져온다.

## 발표·제출 조건

| 항목 | 기준 |
| --- | --- |
| 제출물 | 발표자료(PPT)와 발표 동영상. 최종보고서, tar와 함께 e-class에 올린다 |
| 진행 | PPT로 진행한다. 발표는 팀원 1명이 해도 된다 |
| 발표 시간 | 원문에 지정이 없다. e-class 공지를 확인한다 |
| 용량 | 동영상이 크면 나머지를 먼저 올리고 동영상만 이메일로 보낸다 |

## 발표의 핵심

배점의 65%가 측정·예측·원인 분석·개선이다. 발표만 봐도 **1단계 측정 → 예측 → 실측 → 어긋난 이유 → 개선 → 어떤 조건에서 어떤 IPC를 쓸 것인가**가 이어져야 한다. 분석은 일반론이 아니라 우리 수치로 말한다.

## 발표자료 구성

서식 별첨이 정한 구성과 분량이다.

| 구성 | 분량 | 넣을 것 |
| --- | --- | --- |
| 표지 | 1쪽 | 과제명, 설계과제 명(공유 캔버스 서버), 팀명, 팀원(학번, 성명) |
| 문제 정의 및 요구사항 | 1~2쪽 | 작은 명령과 큰 화면이 섞인 통신, 요구사항 요약 |
| IPC 기초 측정 | 1~2쪽 | 측정 환경, 크기별 지연 그래프, 순위가 바뀌는 지점 |
| 워크로드 명세와 예측 | 1쪽 | 워크로드 표, 예측과 근거 |
| 시스템 설계 | 2~3쪽 | 구성도, 스레드 표, 공유 자원과 동기화 |
| 구현 내용 | 2~3쪽 | 전송 계층 인터페이스, 버전별 핵심 코드, 실행 화면 |
| 성능 분석 | 2~3쪽 | 예측 대비 실측, 원인 확인 실험, 개선 전후, 가이드라인 |
| 팀워크 | 1쪽 | 역할 분담, 작업 시간 |
| 결론 및 AI 활용 | 1쪽 | 총평, AI 활용 방식, AI가 틀린 사례 |

## 데모 시나리오

보고서 5.2절과 동영상의 데모 장면이다. 명령은 구현 뒤 [README의 사용 방법](../../README.md#사용-방법)에 맞춰 채운다.

1. `ipcs`로 시작 전에 자원이 없음을 보인다.
2. 서버를 실행한다.
3. 클라이언트 2개 이상을 서로 다른 시드로 동시에 실행한다.
4. 실행 중 `ipcs`로 만들어진 자원을, `ls /proc/<pid>/task`로 스레드 수를 보인다.
5. 클라이언트가 끝나며 출력하는 지연·처리량 통계를 보인다.
6. 서버를 Ctrl+C로 끝낸다. 저장된 캔버스 이미지와 체크섬을 보인다.
7. 검증기의 정답 체크섬과 같음을 보인다.
8. 락을 끄고 다시 돌려 체크섬이 어긋나는 것을 보인다.
9. `ipcs`로 남은 자원이 없음을 보인다.
10. 다른 IPC 버전으로 3~7을 반복해 같은 체크섬이 나오는 것을 보인다.

## 작성·제출 점검

- 슬라이드 제목은 주장을 담은 문장으로 쓴다. 예: `1단계 결과` 대신 측정에서 확인한 사실을 한 문장으로 쓴다. 수치가 들어간 주장은 확인한 결과만 쓴다.
- 그래프마다 축, 단위, 측정 조건을 표시하고 말로도 설명한다. 같은 조건의 세 IPC를 한 그래프에 그린다.
- 터미널 글자가 화면에서 읽히는 크기인지 확인한다.
- 실행하지 않은 결과, 측정하지 않은 수치를 넣지 않는다.
- 동영상이 끝까지 재생되고 소리가 들리는지 확인한다.
