## 3.1 워크로드 명세

여러 사람이 한 캔버스에 작은 붓으로 자주 그리고, 가끔 화면 일부를 새로 받아 가는 상황을 흉내 낸다. 작은 요청과 큰 응답이 섞이는 것이 이 응용의 특징이다.

| 항목 | 내용 |
| --- | --- |
| 메시지 종류와 크기(분포) | 요청은 모두 40B 이하다(DRAW 40B, SNAPSHOT 32B, HELLO·STATS·BYE 24B, 머리 24B 포함). 응답은 DRAW가 56B(머리 + 서버 시각 32B), SNAPSHOT이 56B + S²B다. 기준 조건(S = 256)의 SNAPSHOT 응답은 65,592B다. 한 실행 안에서 DRAW 사각형과 SNAPSHOT 영역의 크기는 고정이고, 위치는 시드로 정한 균등 난수다 |
| 요청 빈도 (클라이언트당) | 생각하는 시간 없이 보낸다(닫힌 고리). 지연 실행(`-f 1`)은 응답을 받자마자 다음 요청을, 처리량 실행(`-f 16`)은 늘 16개를 띄워 둔다. 빈도는 시스템이 처리하는 만큼이며, 정해진 요청 수(클라이언트마다 20,000개)를 다 보내면 끝난다 |
| 통신 패턴 | 요청·응답(RPC). 요청은 모든 클라이언트가 채널 하나로 서버에 보내고(N:1), 응답은 클라이언트마다 따로 받는다(1:1). 올라가는 쪽은 작고 내려오는 쪽만 크다 |
| 서버 공유 자료구조와 읽기/쓰기 비율 | 캔버스 1MB(타일 64 × 64, 256개). 요청 수로는 쓰기(DRAW) 90%, 읽기(SNAPSHOT) 10%다. 건드리는 칸 수로는 DRAW가 256칸(타일 1~4개), SNAPSHOT이 65,536칸(타일 16~25개)이라, 요청 10개마다 읽기 65,536칸, 쓰기 2,304칸으로 읽기가 약 28배다 |
| 동시 클라이언트 수 | 기준 4개. 클라이언트 수 실험은 1, 2, 4, 8개 |

우리 응용에서 중요한 지표는 **처리량**이다. 여러 사람이 동시에 그리는 동안 서버가 초당 몇 개의 요청을 소화하는지가 응용의 쓸모를 정한다. IPC 비교의 중심(P4~P6)은 처리량 실행으로 하고, 요청 종류별 비용(P1~P3)은 지연 실행과 처리량 실행을 함께 본다.

기준 실험 조건 (클라이언트와 서버 옵션 값)

| 옵션 | 값 | 정한 이유 |
| --- | --- | --- |
| DRAW 비율 `-m` | 90 | 그리기가 대부분이고 화면 갱신은 가끔이다. 아래 P6의 계산으로는 shm과 mq의 처리량 순위가 DRAW 83~92%에서 바뀌므로, 기준이 그 근처에 있어 작은 메시지와 큰 메시지의 영향을 함께 볼 수 있다 |
| DRAW 사각형 `-r` | 16 | 작은 붓(256칸). 서버의 그리기 연산을 작게 해 IPC 비용이 가려지지 않게 한다([구현 계획의 실패 점검](../design/plan.md#리스크-및-미결정)) |
| SNAPSHOT 영역 `-S` | 256 | 화면 일부(64KB). 1단계에서 세 IPC의 차이가 실행 사이 흔들림보다 커지기 시작한 크기가 64KB다([1단계 측정 결과](../measurement/stage1.md#결과)) |
| 동시 요청 수 `-f` | 16 (처리량), 1 (지연) | 1단계 처리량 측정과 같은 값이라 1단계 수치를 그대로 근거로 쓸 수 있다 |
| 워커 수 `-w` | 4 | 클라이언트 수와 같게 둔다. 워커 수 실험은 1, 2, 4, 8([2단계 실험](../measurement/README.md#2단계-실험)) |
| 락 방식 `-l` | global | 기준선 |
| 타일 크기 `-t` | 64 | 기본값. `global`에서는 쓰이지 않는다 |
| 시드 `-s` | 클라이언트 번호 + 1 | 같은 명령이면 세 버전이 같은 요청열을 받는다(F-7) |

1단계 값을 응용에 옮긴 방법. 계산은 위 표의 값으로만 했고, 서버 안쪽 비용은 1단계에 없어 넣지 않았다.

- **한 방향 몫**: 1단계 echo는 요청과 응답이 같은 크기라, 큰 메시지의 왕복에는 큰 전송이 두 번 들어 있다. 응용은 응답만 크다. 그래서 큰 응답 하나의 추가 비용을 (크기 S의 왕복 − 64B의 왕복) / 2로 본다. 전송 비용이 두 방향에서 같다고 가정한 것이다. 클라이언트 1의 지연 중앙값으로 계산하면 다음과 같다.

  | 응답 크기 | pipe | mq | shm |
  | --- | --- | --- | --- |
  | 16KB | 6.1µs | 5.6µs | 1.4µs |
  | 64KB | 35.5µs | 12.0µs | 13.7µs |
  | 256KB | 103.5µs | 49.6µs | 37.5µs |
  | 1MB | 538.4µs | 192.6µs | 226.2µs |

- **처리량 모형**: 처리량 실행에서 메시지 하나에 드는 시간을 1 / (1단계 초당 메시지 수)로 본다. 작은 요청은 1단계 64B, 큰 응답은 1단계의 같은 크기 값을 쓴다. 큰 응답에 대해서는 두 가지로 계산해 범위로 낸다. 1단계 값을 그대로 쓰면 큰 전송이 두 번 들어 있어 응용보다 느린 쪽(하한)이고, 위의 한 방향 몫처럼 64B와의 차이를 절반으로 줄이면 빠른 쪽(상한)이다. 섞인 워크로드는 메시지 시간을 DRAW 비율로 가중 평균한다.
- 두 계산 모두 서버의 작업 큐, 워커, 락, SNAPSHOT 복사가 빠져 있다. 이 비용은 세 IPC에 같게 더해지므로, 아래 비율과 순위는 실제보다 차이가 크게 나오는 쪽이고 절대값은 실제보다 높게 나오는 쪽이다.

예측

| 번호 | 조건 | 예측 (어떤 IPC가 얼마나) | 근거 |
| --- | --- | --- | --- |
| P1 | DRAW만 (`-m 100`, 클라이언트 1) | **지연**: 세 IPC의 중앙값 차이가 실행 사이 흔들림보다 작아 순위가 갈리지 않는다(pipe ≈ mq ≈ shm). 구간별 시간에서 요청 전송 + 응답 전송의 합은 세 IPC 모두 8~9µs 근처(4~14µs)이고, 왕복 지연은 그보다 서버 구간(큐 대기 + 락 대기 + 처리)만큼 길다. **처리량**: mq가 가장 높고 pipe와 shm은 비슷하다(mq > pipe ≈ shm). 절대값은 세 IPC 모두 1단계 64B 값보다 낮다 | 요청 40B, 응답 56B는 1단계 64B에 해당한다. 64B 지연 중앙값 9.07 / 8.13 / 9.30µs의 차이(최대 1.17µs)가 실행 사이 편차(20~59%)보다 작다. 처리량은 64B·클라이언트 1에서 mq 700,173, shm 503,087, pipe 464,034로 1단계 순위가 `mq > pipe ≈ shm`였다. 응용은 서버 안에 작업 큐와 워커를 한 번 더 거친다 |
| P2 | SNAPSHOT 16KB만 (`-m 0 -S 128`, 클라이언트 1) | **지연**: 순위가 갈리지 않는다(pipe ≈ mq ≈ shm). **처리량**: shm > mq ≥ pipe. shm은 mq의 1.5~2.0배, mq는 pipe의 1.2~1.25배 | 16KB 응답의 한 방향 몫이 pipe 6.1, mq 5.6, shm 1.4µs로 차이가 5µs 안이고, 1단계 16KB 지연도 이미 `≈`였다. 처리량 모형으로 pipe 134,061~208,000, mq 159,884~260,000, shm 318,250~390,000(초당 메시지)이 나온다 |
| P3 | SNAPSHOT 1MB만 (`-m 0 -S 1024`, 클라이언트 1) | **지연**: mq ≈ shm < pipe. 왕복 지연은 pipe가 mq의 2.0~2.7배다. 응답 전송 구간(`resp_us`)은 pipe 약 540µs, mq 약 195µs, shm 약 230µs이고, 각각 이 값의 0.5~2배 안에 든다. **처리량**: shm > mq > pipe. mq는 pipe의 약 1.5배, shm은 mq의 2~4.8배다. shm과 mq의 차이는 1단계(4.8배)보다 작아진다 | 1MB 응답의 한 방향 몫이 pipe 538.4, mq 192.6, shm 226.2µs이고, 1단계 1MB 지연은 `mq ≈ shm < pipe`(1,085.85 / 393.39 / 461.75µs)였다. 왕복 비율은 서버 비용 없이 (9.07 + 538.4) / (8.13 + 192.6) = 2.7배이고, 세 IPC에 같게 더해지는 서버의 1MB 복사가 이 비율을 줄인다. 처리량 모형의 비율은 shm/mq 4.7~4.8, mq/pipe 1.5다. 서버가 요청마다 캔버스 1MB를 락 안에서 복사하는 비용은 1단계에 없고, 복사가 가장 적은 shm이 이 공통 비용에 가장 크게 깎인다 |
| P4 | 기준 혼합 워크로드의 처리량 (클라이언트 4, `-f 16`) | mq와 shm의 차이는 1.3배 안쪽이고, 둘 중 어느 쪽이 높은지는 정하지 않는다. mq는 pipe의 1.3~1.4배이고, shm은 pipe보다 낮지 않다(1.0~1.5배). 1단계 64KB·클라이언트 4에서 shm이 mq의 3.3배였던 것과 달리, 혼합 워크로드에서는 shm이 크게 앞서지 않는다 | 처리량 모형(DRAW 90%, SNAPSHOT 64KB, 클라이언트 4)으로 pipe 149,000~240,000, mq 206,000~314,000, shm 224,000~242,000(초당 메시지)이 나온다. 하한 계산에서는 shm이 mq의 1.09배, 상한 계산에서는 mq가 shm의 1.30배라 순위가 계산 방법에 따라 갈린다. shm은 64KB 응답에서 빠르지만(1단계 94,946 vs mq 28,463) 64B 요청에서는 클라이언트 4일 때 가장 느려(263,822 vs mq 667,320, pipe 619,537), 요청의 90%인 DRAW에서 잃는다 |
| P5 | 클라이언트 수를 1 → 8로 늘릴 때 (기준 혼합, `-f 16`) | 총 처리량은 세 IPC 모두 늘지 않고 줄어든다. 클라이언트 8의 처리량은 클라이언트 1의 pipe 0.85~0.95배, mq 0.65~0.75배, shm 0.45~0.5배로, shm이 가장 많이 떨어진다. 클라이언트 1에서는 shm이 가장 높지만(mq의 1.3~1.7배), 클라이언트 8에서는 세 IPC가 1.3배 안으로 모여 순위가 갈리지 않는다 | 1단계 처리량은 클라이언트마다 16개를 띄워 두면 클라이언트 1에서 이미 한계에 가까웠고, 클라이언트를 늘리면 64B(shm 503,087 → 212,877)와 64KB(mq 33,505 → 21,122) 모두 줄었다. 처리량 모형의 클라이언트 8 / 클라이언트 1 비율은 pipe 0.87~0.91, mq 0.69~0.73, shm 0.45~0.48이고, 클라이언트 8의 값은 pipe 151,000~232,000, mq 162,000~256,000, shm 189,000~200,000이다 |
| P6 | 순위가 뒤바뀌는 지점 | **DRAW 비율**: 클라이언트 4의 처리량에서 shm과 mq의 순위는 DRAW 83~92% 사이에서 바뀐다. 그보다 SNAPSHOT이 많으면 shm, DRAW가 많으면 mq가 높다. shm과 pipe는 DRAW 91~96% 사이에서 바뀐다. 클라이언트 1에서는 DRAW 96% 이상이 되어야 mq가 shm을 앞선다. **응답 크기**: SNAPSHOT만 보낼 때 클라이언트 1의 64KB 지연에서 pipe와 나머지의 차이는 1단계(mq의 2.5배)보다 줄어 1.5~2.2배다 | 처리량 모형에서 DRAW 비율을 1%씩 바꿔 shm이 mq(또는 pipe)보다 낮아지는 첫 비율을 찾았다. 하한 계산은 92%(pipe와는 96%), 상한 계산은 83%(91%)다. 클라이언트 1은 96~98%다. 64KB의 한 방향 몫으로 계산한 왕복은 pipe 9.07 + 35.5 = 44.6µs, mq 8.13 + 12.0 = 20.1µs로 2.2배이고, 공통 서버 비용이 더해지면 줄어든다 |

1단계 벤치마크에 없어서 예측이 틀릴 수 있다고 보는 요인

- **응답만 큰 비대칭**: 한 방향 몫을 왕복 차이의 절반으로 가정했다. pipe는 64KB 버퍼를 채울 때마다 양쪽이 잠들어 방향마다 비용이 다를 수 있다.
- **서버 안쪽 단계**: 수신 스레드 → 작업 큐 → 워커로 깨우기가 한 번 더 있고, 전역 락을 워커 4개가 다투며, SNAPSHOT마다 캔버스를 응답 버퍼로 복사한다(64KB~1MB). 이 비용이 IPC 비용보다 크면 세 IPC가 모두 비슷해진다. 그때는 구간별 시간에서 큐 대기와 락 대기가 가장 크게 나타날 것이다.
- **스레드 수**: 기준 조건에서 클라이언트 4 × 3 + 서버 워커 4 + 2 = 18개(mq는 감시 스레드 5개를 더해 23개)로 논리 CPU 12개를 넘는다. 클라이언트 8이면 30개가 넘는다. 대부분 막혀 기다리지만, 처리량이 꺾이는 원인이 IPC가 아니라 CPU 부족일 수 있다.
- **pipe의 긴 꼬리**: 1단계 처리량에서 pipe는 `PIPE_BUF`를 넘는 요청의 송신 잠금 때문에 클라이언트가 2개 이상이면 최대 지연이 크게 튀었다. 응용의 요청은 40B 이하라 이 잠금을 쓰지 않으므로, 클라이언트가 많을 때 pipe가 1단계보다 나을 수 있다.
- **mq의 큐 경쟁**: 1단계에서는 요청도 커서 요청 큐(16KB) 하나를 큰 조각들이 다퉜다. 응용은 요청이 작아 요청 큐의 경쟁이 줄고, 응답 큐 하나를 모든 클라이언트가 나누는 것만 남는다. mq가 클라이언트가 많을 때 1단계보다 나을 수 있다.
- **작은 메시지의 흔들림**: 16KB 이하에서 실행 사이 편차가 9~85%였다. P1과 P2의 지연은 순위가 갈리지 않는다고만 예측했다.
