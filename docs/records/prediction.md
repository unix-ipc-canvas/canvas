보고서 3장의 원본이다. **서버·클라이언트를 구현하기 전에 작성해 커밋했고, 이후 위쪽은 고치지 않는다.** 바뀐 생각은 맨 아래 [수정 기록](#수정-기록)에만 덧붙인다(요구사항 C-10).

## 워크로드 명세

### 사람 한 명의 통신 (설계 기준)

그림판을 쓰는 사람 한 명을 기준으로 잡고, 부하 클라이언트는 이 비율을 그대로 쓰되 쉬지 않고 보낸다.

- 붓을 끄는 동안 마우스 이벤트마다 DRAW 하나를 보낸다. 마우스 이벤트는 약 60회/s다.
- 보고 있는 영역을 150ms마다 다시 받는다(SNAPSHOT 약 6.7회/s). 한 번에 받는 영역은 최대 256 × 256칸이다(터미널 한 화면에 들어가는 크기와 비슷하다).
- 그래서 요청 수로 DRAW : SNAPSHOT ≈ 60 : 6.7 ≈ 90 : 10이다.

### 메시지 크기

모든 메시지는 머리 24B(`msg_hdr_t`) + payload다. 응답 payload는 항상 서버 시각 32B(`srv_ts_t`)로 시작한다.

| 메시지 | 요청 (B) | 응답 (B) | 비율 (요청 수) |
| --- | ---: | ---: | ---: |
| DRAW 16 × 16 | 40 | 56 | 90% |
| SNAPSHOT 256 × 256 | 32 | 65,592 | 10% |
| HELLO, BYE, STATS | 24 | 56~120 | 클라이언트마다 처음·끝 몇 개 |

- 요청 하나당 평균: 요청 39B, 응답 0.9 × 56 + 0.1 × 65,592 = 6,610B. **응답 바이트의 99.2%가 SNAPSHOT이다.**
- 요청은 모두 `PIPE_BUF`(4,096B) 이하, `msgmax`(8,192B) 이하다. SNAPSHOT 응답만 `msgmax`보다 커서 mq에서 조각 9개로 나뉜다.

### 워크로드 표 (보고서 3.1절)

| 항목 | 내용 |
| --- | --- |
| 메시지 종류와 크기(분포) | DRAW 요청 40B / 응답 56B (90%), SNAPSHOT 요청 32B / 응답 65,592B (10%). DRAW 사각형 16 × 16, 위치는 그림판 안에서 균등 분포, 값 v는 1~255 균등. SNAPSHOT 영역 256 × 256, 위치 균등 |
| 요청 빈도 (클라이언트당) | 사람 기준 약 67 요청/s(DRAW 60 + SNAPSHOT 6.7). 부하 클라이언트는 응답을 받는 즉시 다음 요청(동시 요청 1, 지연 측정) 또는 16개를 띄워 둠(처리량 측정) |
| 통신 패턴 | N:1 요청(모든 클라이언트 → 서버 요청 채널 하나), 1:N 응답(서버 → 클라이언트별 응답 채널), 요청-응답(닫힌 고리), 요청 작고 응답 큰 비대칭 |
| 서버 공유 자료구조와 읽기/쓰기 비율 | 그림판 K개(각 1MB)와 타일 락, 작업 큐, 통계, 클라이언트 표. 요청 수로 쓰기(DRAW) 90 : 읽기(SNAPSHOT) 10, 건드리는 칸 수로 쓰기 230 : 읽기 6,554(3.4 : 96.6) |
| 동시 클라이언트 수 | 1, 4, 16, 64, 256, 1024. 그림판 8개에 번호 순으로 고르게 나눈다(클라이언트 i → 그림판 i mod 8) |

### 목표 부하 (요구사항 N-2)

사람 1024명이 동시에 그리면 DRAW 61,440/s + SNAPSHOT 6,827/s ≈ **68,000 요청/s**, 응답 6,827 × 65,592B ≈ **448MB/s**다. 이때 DRAW 왕복 지연 상위 99%가 16.7ms(한 프레임) 이하여야 한다.

### 어느 지표가 더 중요한가

사람이 쓰는 그림판이라 **DRAW의 꼬리 지연(상위 99%)이 사용감을 정하고, 처리량은 서버 하나가 받을 수 있는 사람 수를 정한다.** 두 지표를 모두 재되, IPC를 고르는 1차 기준은 "목표 부하에서 DRAW 상위 99%가 한 프레임 안인가"이고, 2차 기준은 최대 처리량이다. 클라이언트가 적을 때는 SNAPSHOT 지연(화면 갱신이 늦는가)도 본다.

## 성능 예측

1단계 echo는 요청과 응답이 같은 크기였다. 응용은 요청이 작고 응답만 크므로, 큰 메시지 비용의 한 방향 몫을 (크기 S의 echo − 64B echo) / 2로 어림한다. 응용에는 1단계 벤치에 없던 비용(수신 스레드 → 작업 큐 → 워커의 넘김, 타일 락, 그림판 복사)이 더해진다. 넘김 한 번은 조건변수로 잠든 워커를 깨우는 비용이라 5~10µs로 잡는다.

| 번호 | 조건 | 예측 | 근거 (1단계 수치) |
| --- | --- | --- | --- |
| P1 | 클라이언트 1, 동시 요청 1, DRAW 지연 | 세 IPC가 구분되지 않는다(≈). DRAW p50은 15~25µs | 요청 40B·응답 56B는 1단계 64B 영역이다. 64B c=1 echo p50이 pipe 9.93, mq 8.36, shm 9.57µs로 순위가 ≈였다. 여기에 넘김 5~10µs가 더해진다 |
| P2 | 클라이언트 1, 동시 요청 1, SNAPSHOT 256 × 256 지연 | mq ≈ shm < pipe. p50은 pipe 50~65µs, mq·shm 25~40µs. pipe가 약 1.7배 | 64KB c=1 echo p50 pipe 82.34, mq 34.72, shm 34.42µs. 한 방향 몫 pipe 36.2, mq 13.2, shm 12.4µs + 작은 요청 약 9µs + 서버(넘김, 64KB 복사) 약 10µs |
| P3 | 클라이언트 1, 동시 요청 16, 기준 혼합(DRAW 90%) 처리량 | shm > mq > pipe. 전송 계층만의 상한은 shm 45만, mq 35만, pipe 23만 요청/s이고 실제는 서버 비용으로 이보다 낮다. shm이 pipe의 약 2배 | c=1 f=16 처리량 64B: pipe 441,732, mq 741,430, shm 512,523 msg/s. 64KB: pipe 22,663, mq 32,111, shm 140,700 msg/s. | P4 | 클라이언트 수 증가, DRAW만, 동시 요청 1 | 클라이언트 64 이상에서 shm의 DRAW 지연이 가장 길다. pipe ≈ mq < shm | 64B c=8 echo p50: mq 23.09, pipe 26.84, shm 38.10µs(`pipe ≈ mq < shm`), 처리량도 shm 14.9MB/s로 가장 낮았다. shm은 요청 링 하나를 모든 클라이언트가 MUTEX·빈 칸 세마포어로 다투며 메시지마다 `semop`이 보내는 쪽 2번 든다. 클라이언트가 많을수록 이 경쟁이 커진다 |
| P5 | 클라이언트 수 증가(1 → 1024), 기준 혼합, 동시 요청 1, 그림판 8 | 처리량 순위가 뒤집힌다. 클라이언트 16 이하는 shm > mq > pipe, 256·1024는 pipe > shm > mq. mq의 SNAPSHOT 상위 99%가 가장 길다 | mq는 응답 큐 하나(용량 `msgmnb` 16,384B)를 모든 클라이언트가 mtype으로 나눠 쓴다. | P7 | 자원 사용량 | 요청 하나당 자발적 컨텍스트 스위치(클라이언트 + 서버, 클라이언트 1): DRAW는 세 IPC 모두 4~5번. SNAPSHOT은 pipe·mq 6~8번 > shm 4~5번. 메모리(클라이언트 1024): shm은 응답 링(클라이언트당 136KB)으로 공유 메모리 약 140MB, pipe·mq 서버는 그림판 8MB + 스레드 스택 수준이라 shm ≫ pipe ≈ mq | 1단계 메시지당 자발적 컨텍스트 스위치: 64B 세 IPC 모두 3.0, 64KB pipe 7.0, mq 7.5, shm 3.0. 응용은 수신 → 워커 넘김으로 1~2번이 더해진다. shm 응답 링 크기는 [설계 명세](../design/README.md#메모리)의 계산 |
| P8 | 목표 부하(사람 1024명 속도, N-2) | pipe와 shm은 DRAW p99 16.7ms 이하를 만족하고, mq는 응답 큐 경쟁으로 넘을 수 있다 | P5와 같은 이유. 목표 부하(68,000 요청/s)는 P3 상한보다 낮지만, mq는 SNAPSHOT 조각(초당 약 61,000개)이 큐 하나를 지나야 한다 |

### IPC 선택 예측

- 클라이언트 16개 이하: **shm**. 응답 바이트의 99%가 64KB SNAPSHOT이고, 1단계에서 64KB 이상은 shm의 처리량이 4배 이상 앞섰다.
- 클라이언트 수백~1024개: **pipe**. 요청이 작아 1단계 작은 메시지에서처럼 세 IPC의 기본 비용은 비슷한데, 클라이언트가 많으면 채널 구조가 결정한다. pipe만 요청 쪽(원자적 쓰기, 잠금 없음)과 응답 쪽(클라이언트별 FIFO) 모두 클라이언트끼리 다투는 지점이 커널 안에만 있다.
- mq는 어느 규모에서도 1위가 되지 않을 것이다. 작은 메시지는 1위일 수 있지만 응답 큐 하나를 모두가 나눠 쓰는 구조가 SNAPSHOT에서 병목이 된다.

### 판정 기준 (6.4절에서 쓰는 방법)

- 순위는 1단계와 같은 규칙으로 정한다. 실행별 값에서 좋은 쪽과 나쁜 쪽을 4분의 1씩 뺀 가운데 범위가 겹치면 ≈로 묶는다([반복과 통계](../measurement/README.md#반복과-통계)).
- 일치: 예측한 순위와 범위가 모두 맞다. 부분 일치: 순위는 맞고 수치 범위가 벗어났거나, 일부 조건에서만 맞다. 불일치: 순위가 다르다.
- 틀린 예측은 원인을 추정하고, 그 요인 하나만 바꾼 실험으로 확인한다([2단계 측정 결과](../measurement/stage2.md)).
