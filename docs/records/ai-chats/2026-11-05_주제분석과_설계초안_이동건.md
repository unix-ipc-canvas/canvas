## 1. 과제 분석

**질문 (11/05)**

> 일단 이 설계 프로젝트에 대해서 지침과 컨택스트를 참고해서 분석해봐

**AI 답에서 쓴 것**

- 배점 구조상 측정·예측·분석·개선이 65%, 구현이 25%라서 "구현은 빨리 끝내고 측정과 분석에 시간을 써야 한다".
- 구현하면 부딪힐 함정 7가지를 들었다.
  - 따로 실행하는 클라이언트를 받으려면 pipe 버전은 FIFO가 필요하다(→ 이슈 #2, 11/23 FIFO로 결정).
  - `PIPE_BUF`(4096B)를 넘는 쓰기는 섞인다(→ 요청을 4KB 이하로 설계).
  - System V mq의 `msgmax` 기본 8192B 때문에 큰 메시지는 나눠 보내야 한다.
  - shm은 알림 수단이 없어 작은 메시지에서는 세마포어 비용이 지배적일 수 있다.
  - `ipcs`는 POSIX IPC를 보여 주지 않는다(→ System V로 통일).
  - Ctrl+C 정리는 `sigwait` 전담 스레드로 한다.
  - 측정에서 `clock_gettime` 비용, p99의 표본 수, CPU 주파수를 챙긴다.
- 전송 계층을 함수 포인터 인터페이스 하나로 만들어 1단계 벤치마크와 2단계 응용이 같은 전송 코드를 쓰게 하자고 제안했다(→ `transport.h`).
- 예측 원본, AI 대화와 오류 사례, 투자 시간 로그는 처음부터 쌓으라고 했다.

## 2. 주제 추천

**질문**

> 이 프로젝트에 대해 더 빡세게 분석해주고 주제를 추천해봐 팀 구성은 완료 됐고 일단 주제만 먼저 정해보게.
> 안내 문서만 읽어서는 구체적으로 뭘 어떻게 하라는건지 감이 잘 안와서 그래.

**AI 답에서 쓴 것**

- 안내문을 7단계 작업(기초 측정 → 워크로드 명세 → 예측 → 구현 → 실측 → 원인 규명 → 개선)으로 풀고, 주제를 고르는 원칙 4가지를 냈다.
  - 예측이 어긋날 구조가 있을 것.
  - 답이 뒤집히는 조건이 응용 안에 있을 것.
  - 서버 연산이 IPC를 덮지 않을 것.
  - 같은 컴퓨터의 시계로 지연을 구간별로 나눌 것.
- 후보 6개(이미지 필터, 로그 수집, 좌석 예약, 공유 캔버스, 키-값 캐시, 주문 매칭)를 비교해 **공유 캔버스 서버**를 추천했다. 채택했다.
  - 작은 DRAW와 큰 SNAPSHOT(최대 1MB)이 섞인다.
  - 픽셀을 더하기(mod 256)로 정의해 체크섬으로 경쟁 상태를 검증한다.
  - 타일 락을 오름차순으로 잡아 교착 상태를 막는다.
- 문제 정의를 X11 MIT-SHM과 Wayland `wl_shm` 사례에 묶자고 했다(보고서 1.1절, 출처는 직접 확인할 것).

**AI가 틀린 부분**

- 같은 답에서 "mq로 1MB를 보내면 8KB 조각마다 송수신이 교대할 가능성"을 말했다. 실제로 재 보니 조각마다 교대하지 않았다. [AI 활용 기록](../ai-log.md) 2번 표 4번에 있다.
