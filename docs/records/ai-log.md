## 2. AI가 틀렸던 사례 (최소 2개)

실제로 확인한 것만 적습니다. "확인 방법"에는 우리가 돌린 명령이나 측정 결과를 적습니다.

| 번호 | 날짜 | AI의 제안·설명 | 실제로 확인한 내용 | 확인 방법과 조치 |
| --- | --- | --- | --- | --- |
| 1 | 11/18 | 우리 System V key 60020~60029 를 16진수 `0xEA6x` 로 계산해, 남은 자원 검사가 `0x0000ea6` 으로 시작하는 key 를 찾게 짰다 | 60020 = `0xEA74` 이다. 우리 key 는 `0xEA74`~`0xEA7D` 이고 `0xEA6x` 는 60000~60015(다른 팀). 검사가 엉뚱한 key 를 봐서 남은 자원이 있어도 늘 통과했다 | 측정 스크립트에 같은 검사를 넣다가 의심. shm 서버를 띄운 채 `ipcs -m -s` 로 실제 key `0x0000ea76`~`0x0000ea79` 를 확인했다. key 를 `verify.sh` 처럼 `printf '0x%08x' $((60000 + 팀번호 * 10 + y))` 로 계산하게 고치고 비정상 종료 검사를 다시 돌렸다(19/19 통과) |
| 2 | 11/18 | 헤더 초안이 `MAX_PAYLOAD`를 "가장 큰 응답 = 캔버스 전체"라며 1024 × 1024B(1MB)로 정했다 | 같은 헤더가 모든 응답 payload 앞에 서버 시각 `srv_ts_t`(32B)를 붙이기로 해서, 캔버스 전체 SNAPSHOT 응답은 1MB + 32B다. 한도보다 32B 크다 | 1MB + 32B 응답을 세 전송 계층으로 보내는 임시 프로그램을 돌렸다. pipe와 mq는 보냈고 shm은 `EMSGSIZE`로 거부해, 세 버전이 보낼 수 있는 최대 크기가 서로 달랐다. `MAX_PAYLOAD`를 `sizeof(srv_ts_t) + 1MB`로 고치고(#4) 같은 시험을 다시 돌려 세 버전 모두 1048608B를 주고받았다 |
| 3 | 11/18 | pipe 서버가 큰 요청 도중 SIGINT 로 끝나지 않는 원인을 "깨우기 메시지가 큰 요청 사이에 끼어든다"로 보고, 코드 주석대로 깨우기를 쓸 때 송신 잠금을 잡게 고쳤다 | 고친 뒤 같은 시험에서 60번 중 55번 멈춰 더 나빠졌다. 수신 스레드가 먼저 끝나 FIFO 가 가득 찬 채 남고, 큰 요청을 쓰던 클라이언트가 잠금을 쥔 채 그 FIFO 에서 막혀 있어 깨우기가 잠금을 영원히 기다렸다. 원인은 끼어듦이 아니라 막히는 쓰기였다 | 클라이언트 3개가 1MB 요청을 보내는 중 SIGINT 를 반복하는 시험으로 고치기 전 40번 중 2번, 잠금 수정 60번 중 55번, 막히지 않는 깨우기(O_NONBLOCK 쓰기 끝) 160번 중 0번 멈춤을 확인하고 마지막 것을 채택했다 |
| 4 | 11/18 | mq 로 1MB 를 보내면 조각(8KB)마다 송수신이 교대한다고 설명했다(아래 '직접 확인해 볼 것' 목록). 조각마다 잠들고 깨므로 큰 메시지에서 mq 가 느릴 것이라는 뜻이다 | 1MB 왕복 한 번에 조각 258개(한 방향 129개)를 주고받는데 클라이언트와 서버의 자발적 컨텍스트 스위치는 합쳐 48.8번이었다. 조각마다 교대한다면 적어도 조각 수만큼은 잠들어야 한다. mq 의 1MB 지연(393µs)도 pipe(1,086µs)보다 짧고 shm(462µs)과 구분되지 않았다 | 1단계 측정(`results/bench_latency.csv`, 1MB·클라이언트 1, 실행 5번의 중앙값, 요약표의 '메시지당 자발적 컨텍스트 스위치'). 논리 CPU 12개에서 보내는 쪽과 받는 쪽이 다른 코어에서 함께 돈 것으로 보고, CPU 하나에 묶으면 교대하는지는 T5 에서 `taskset` 으로 확인한다([1단계 측정 결과의 해석](../measurement/stage1.md#해석)) |

AI가 한 말 중 우리 컴퓨터에서 직접 확인해 볼 것 (틀렸으면 위 표로 옮기기)

- [x] System V 메시지 최대 크기 8192B, 큐 용량 16384B → `cat /proc/sys/kernel/msgmax /proc/sys/kernel/msgmnb`. 11/18 측정용 컴퓨터에서 8192, 16384(`results/bench_env.txt`). 맞았다
- [x] 파이프 버퍼 기본 64KB, PIPE_BUF 4096B → `fcntl(fd, F_GETPIPE_SZ)`, `getconf PIPE_BUF /`. 11/18 측정용 컴퓨터에서 65536, 4096. 맞았다. pipe 의 메시지당 컨텍스트 스위치도 64KB 단위로 늘었다(1단계 측정)
- [x] "작은 메시지에서는 shared memory가 pipe보다 빠르지 않을 수 있다" → 1단계 64B 측정. 클라이언트 1 의 지연 중앙값이 pipe 9.07µs, shm 9.30µs 로 구분되지 않았고, 클라이언트 8 에서는 shm 이 가장 느렸다(37.74µs). 맞았다
- [x] "mq로 1MB를 보내면 조각마다 송수신이 교대한다" → 1단계 1MB 측정의 자발적 컨텍스트 스위치 수. 틀렸다(위 표 4번)
- [ ] AI가 설계 문서에 적은 그 밖의 숫자와 예상 전부

지금까지 확인된 것

- 11/12 이동건 PC(Ubuntu, 커널 7.0.0)에서 `msgmax` 8192, `msgmnb` 16384, `PIPE_BUF` 4096, `pipe-max-size` 1048576을 확인했다. AI의 설명과 같았다. 측정용 컴퓨터에서 다시 확인한다.
- 11/12 AI가 캔버스 저장 형식을 PPM이라고 적어 왔으나, 한 칸 1바이트 회색조는 PGM이 맞다. AI가 문서를 다시 쓰다가 스스로 고쳤다. 사례로 쓸지는 팀이 정한다.

## 3. AI 생성 코드의 결함

| 날짜 | 파일 | 결함 (경쟁 상태, 교착 상태, 자원 미해제, 오류 처리 누락 등) | 어떻게 찾았나 | 수정 내용 |
| --- | --- | --- | --- | --- |
| 11/16 | `src/transport/transport_pipe.c` | `true`, `false`를 쓰면서 `<stdbool.h>`를 넣지 않아 빌드 실패 | `make EXTRA_CFLAGS=-Werror` 컴파일 오류 | `#include <stdbool.h>` 추가 |

## 4. AI가 제시한 대안과 채택·기각 (설계 결정 근거)

AI가 낸 대안 가운데 무엇을 고르고 무엇을 버렸는지, 그 이유를 적는다. 강의(생성형 AI 활용)가 평가 항목으로 든 "설계 결정 근거"다. 고른 사람은 그 일의 담당이고, 결정의 원본은 괄호 안의 문서나 코드 주석이다.
