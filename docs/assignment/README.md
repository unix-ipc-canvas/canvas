## 핵심 목표

**공통 주제: 내 응용에 맞는 IPC는 무엇인가 — 예측하고, 구현하고, 검증하라.** 3가지 버전 구현은 출발점이고, 평가의 중심은 측정 결과를 해석하고 설계를 개선하는 과정이다.

| 단계 | 내용 |
| --- | --- |
| 1단계 (공통) | 구현에 쓴 컴퓨터에서 3가지 IPC의 지연시간·처리량을 측정하고 해석 |
| 2단계 (팀 응용) | 워크로드 정의 → 1단계 근거로 예측 → 3버전 구현·측정 → 예측과 실제의 차이 분석 → 설계 개선 |

## 일정과 수행 조건

| 항목 | 내용 |
| --- | --- |
| 팀 구성 | 2026년 11월 10일(화), e-class에 팀명·팀장·팀원 등록 |
| 최종 제출 | **2026년 11월 30일(월)**, e-class 업로드 시각 기준 |
| 팀 | 3인 1조. 팀원이 pipe, message queue, shared memory를 1개씩 맡아 구현 |
| 측정 | 1단계 측정과 2단계 분석은 팀원 모두가 함께, **모든 버전을 같은 컴퓨터에서** |

중간 제출물은 없다. 2단계 예측은 반드시 구현 전에 작성한다.

## 1단계: IPC 기초 성능 측정

응용 기능 없이 데이터만 주고받는 벤치마크를 3가지 IPC로 작성한다.

| 구분 | 요건 |
| --- | --- |
| 측정 항목 | 왕복 지연시간(ping-pong: 보낸 뒤 같은 크기 응답을 받을 때까지), 처리량(초당 메시지 수와 바이트 수) |
| 메시지 크기 | 5단계 이상 (예: 64B, 1KB, 16KB, 256KB, 1MB) |
| 동시 클라이언트 수 | 1, 2, 4, 8 |
| 보고서 | 측정 환경, 크기별·클라이언트 수별 그래프(3가지 IPC를 한 그래프에), 결과 해석 |

위 범위는 최소 기준이며 변인을 추가할 수 있다. 해석은 우리 컴퓨터에서 나온 숫자를 근거로 쓴다. 순위가 뒤바뀌는 지점과 그 이유를 설명해야 한다.

## 2단계: 팀 응용 설계와 검증

| 절차 | 요건 |
| --- | --- |
| 응용 기획 | 클라이언트-서버 구조 |
| 워크로드 명세 | 메시지 종류와 크기(분포), 요청 빈도, 통신 패턴, 공유 자료구조의 읽기/쓰기 비율 |
| 예측 | 구현·측정 전에 작성. 보고서에 작성 당시 내용 그대로 싣고, 수정하면 무엇을 왜 바꿨는지 따로 표시 |
| 구현 | 같은 응용을 3버전으로. 응용 로직은 공통 모듈, IPC 부분만 버전별로 (권장) |
| 검증 | 예측과 실측 비교. 틀린 부분의 원인은 **그 요인만 바꾼 추가 실험**으로 확인 |
| 설계 개선 | 1회 이상. 개선 전후를 측정해 비교 |

응용 주제 조건은 네 가지다.

- 데이터 양이나 통신 빈도가 IPC 선택이 성능에 영향을 줄 만큼 의미 있을 것
- 서버에 여러 스레드가 함께 접근하는 공유 자료구조가 있을 것
- 클라이언트를 2개 이상 동시에 실행할 수 있을 것
- 단순 채팅 서버, 단순 메시지 중계(받은 메시지를 그대로 다른 클라이언트에 전달)는 인정하지 않음

## 측정 방법 필수 요건

1단계와 2단계 모두 지키고, 보고서에 측정 방법을 구체적으로 쓴다. 우리가 이를 어떻게 지키는지는 [측정 방법](../tech-specs/03-measurement.md)에 둔다.

| 요건 | 내용 |
| --- | --- |
| 시간 측정 | `clock_gettime(CLOCK_MONOTONIC, ...)`. 타임스탬프를 찍은 위치와 그 이유를 명시 |
| 반복 측정 | 워밍업 후 측정, 조건마다 30회 이상 권장. 평균과 함께 중앙값, 최대값(또는 상위 99%) 보고 |
| 지표 구분 | 지연시간과 처리량을 구분해 측정하고, 응용에 어느 쪽이 더 중요한지 설명 |
| 자원 사용량 | `getrusage()`의 CPU 시간과 컨텍스트 스위치(자발적/비자발적), `/proc/self/status`의 VmRSS 등 |
| 간섭 최소화 | 측정 구간 안에서 `printf` 등 출력 금지, 다른 무거운 프로그램 종료, 측정 코드의 영향 고려 |
| 원인 분석 근거 | 추측이 아니라 근거로. `strace -c`, `/usr/bin/time -v`, 동기화 대기 시간 측정 등 |
| 원자료 보존 | 측정 원자료(CSV 등)와 스크립트를 제출물에 포함해 재현 가능하게 |

## 제한 요건과 실행 환경

- 경쟁 상태가 생기지 않도록 동기화하고, 어떤 기법을 왜 골랐는지 설명한다.
- 성능을 높이는 방안과 메모리 사용량을 줄이는 방안을 설계에 반영하고 효과를 측정으로 확인한다.
- 표준 UNIX(POSIX) 도구와 API를 쓰고 **make를 필수로** 쓴다.
- 클라이언트와 서버 모두 **프로세스별 스레드 3개 이상**을 쓴다.
- 종료할 때 IPC 자원(message queue, shared memory, semaphore)을 정리하고, 실행 후 `ipcs` 결과를 보고서에 넣는다.
- Linux에서 개발·측정한다. 네이티브, 가상머신, WSL2 모두 허용한다.
- 보고서에 측정 환경(CPU 모델, 코어 수, 메모리, 배포판과 커널, gcc 버전, 가상화 여부)을 기록한다.
- 채점은 Ubuntu Linux + gcc에서 make로 컴파일해 실행을 확인한다.
- System V IPC의 key는 **60xxy** (xx = 팀 번호, y = 0~9). POSIX IPC의 이름은 `/osproject_조번호_용도`.

## 생성형 AI 활용 규정

자유롭게, 적극적으로 쓰되 다음을 지킨다. 기록 위치는 [AI 활용 기록](../records/ai-log.md)이다.

- 측정 데이터는 반드시 직접 측정한 값이어야 한다. AI가 제시한 수치를 측정값처럼 쓰지 않는다.
- 보고서에 어느 단계에서 어떻게 썼는지 주요 프롬프트 예시와 함께 쓰고, 주요 대화 기록을 부록에 첨부한다.
- AI의 제안이나 설명이 틀렸거나 우리 측정과 맞지 않았던 사례를 **2개 이상** 쓰고, 어떻게 확인하고 바로잡았는지 설명한다.
- AI가 생성한 코드에서 발견한 문제(경쟁 상태, 교착 상태, 자원 미해제, 오류 처리 누락)도 쓴다.

## 원문에 없거나 확인이 필요한 것

- **작업 시간 표시**: 원문 3개에는 없고 이동건의 수업 메모에 있는 조건이다. 서식에 자리가 없어 7장 팀워크 표에 열을 추가하는 것으로 한다.
- **FIFO 인정 여부**: 원문은 "pipe"라고만 쓴다. 이름 있는 파이프(FIFO)를 pipe 버전으로 인정하는지 교수님께 확인한다.
- **발표 동영상 길이**: 원문에 지정이 없다. e-class 공지를 확인한다.
- **팀 번호**: 2팀으로 반영했다. e-class 등록 결과와 다르면 `Makefile`의 `TEAM_NO`를 고친다.
