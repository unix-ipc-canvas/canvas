# 발표 질의응답 준비 — shm 전송 계층과 측정 (C 담당)

[문서 안내](../../README.md#관련-문서)

C 담당(shm 전송 계층, 측정)이 발표와 질의응답에서 직접 설명할 수 있게, 나올 만한 질문과 코드·측정에 근거한 답을 모았다. 답은 [transport_shm.c](../../src/transport/transport_shm.c)의 주석과 코드, [측정 방법](../measurement/README.md), [1단계](../measurement/stage1.md)·[2단계 측정 결과](../measurement/stage2.md)에서 왔고 수치도 거기서 옮겼다. 외워서 읽기보다 코드를 열어 놓고 각 답이 어느 줄에 해당하는지 짚어 보며 연습한다(맨 아래 [직접 해 보기](#직접-해-보기)).

## shm 전송 계층

**Q1. 공유 메모리에 무엇을 어떻게 두었나?**
요청 영역과 응답 영역, 두 공유 메모리 세그먼트를 둔다. 요청 영역에는 모든 클라이언트가 함께 쓰는 링 버퍼 하나가, 응답 영역에는 클라이언트마다 하나씩 링 16개(`MAX_CLIENTS`)가 있다. 링은 같은 크기의 칸(기본 4096B)으로 나뉘고, 메시지 하나(머리 24B + payload)는 칸의 처음부터 이어진 칸 k개를 차지한다. 끝에 닿으면 처음으로 이어 쓴다. 머리는 항상 첫 칸 안에 있다. key는 팀 번호로 정한 60020~60029 범위(요청 shm 2, 응답 shm 3, 세마포어 4·5)다.

**Q2. 링 하나에 세마포어가 몇 개이고 각각 무엇을 하나?**
세 개다. `MUTEX`는 보내는 쪽끼리 한 번에 하나만 쓰게 한다(요청 링은 여러 클라이언트, 응답 링은 여러 워커가 보낸다). `FREE`는 빈 칸 수, `MSGS`는 다 쓴 메시지 수다. 보내기는 `semop {FREE -k, MUTEX -1}` → 복사 → head += k → `semop {MSGS +1, MUTEX +1}`, 받기는 `semop {MSGS -1}` → 복사 → tail += k → `semop {FREE +k}`다.

**Q3. 빈 칸과 MUTEX를 왜 한 번의 semop으로 얻나?**
두 번에 나눠 얻으면 MUTEX를 쥔 채 빈 칸을 기다리거나, 빈 칸을 잡아 둔 채 MUTEX를 기다리게 된다. 앞의 경우 MUTEX를 쥔 쪽이 잠들어 다른 송신자가 모두 막히고, 받는 쪽이 칸을 비워도 MUTEX를 기다리던 쪽은 진행하지 못한다. `semop`은 여러 연산을 원자적으로 한꺼번에 하거나 하나도 하지 않으므로, 기다리는 동안에는 아무것도 쥐고 있지 않다. 교착 상태가 생기지 않는다.

**Q4. 받는 쪽 tail에는 왜 잠금이 없나?**
링마다 받는 쪽이 하나뿐이기 때문이다. 요청 링은 서버 수신 스레드 하나, 응답 링은 그 클라이언트의 수신 스레드 하나만 읽는다. tail을 바꾸는 스레드가 하나라 경쟁이 없다. head는 여러 송신자가 바꾸므로 MUTEX가 보호한다.

**Q5. head를 원자적 변수로 읽고 쓴 이유는? MUTEX가 보호하면 충분하지 않나?**
보호는 MUTEX(세마포어)가 한다. 원자적 읽기·쓰기(acquire/release)는 그 순서를 C 메모리 모델로도 드러내기 위해서다. ThreadSanitizer는 `semop`을 동기화로 보지 못해서, 보통 변수로 두면 같은 프로세스의 두 워커가 잠금 없이 head를 쓰는 것처럼 경고한다. x86에서는 보통의 읽기·쓰기와 같은 명령이라 비용이 없다.

**Q6. 보내는 도중 프로세스가 kill -9로 죽으면?**
`FREE -k`와 `MUTEX -1`에 `SEM_UNDO`를 붙였다. 프로세스가 죽으면 커널이 되돌려서 MUTEX가 풀리고 잡아 둔 빈 칸도 돌아온다. 다 쓴 뒤에는 `FREE`에 +k(SEM_UNDO)와 -k를 함께 해서 값은 그대로 두고 되돌리기 기록만 지운다. 이 시나리오는 T-04 전송 계층 시험(클라이언트 `kill -9`, 서버 `kill -9`)이 확인한다.

**Q7. 세마포어를 기다리다가 상대가 죽으면 영원히 멈추지 않나?**
그래서 기다릴 때는 `semtimedop`으로 200ms(`WAIT_MS`)마다 깨어나 상대가 살아 있는지 본다. 살아 있는 표시는 잠금 파일 `/tmp/osproject_2_shm.lock`의 바이트 잠금이다(바이트 0 서버, 바이트 1 + id 클라이언트). 프로세스가 죽으면 커널이 그 잠금을 풀기 때문에, `F_OFD_GETLK`로 잠금이 풀린 것을 보면 상대가 죽은 것이다. 기다리지 않고 바로 통과하는 보통의 송수신에서는 이 확인을 하지 않아 비용이 없다.

**Q8. 프로세스 공유 mutex와 조건변수(pthread)를 쓰지 않고 System V 세마포어를 쓴 이유는?**
세 가지 때문에 세마포어로 정했다(코드의 DECISION 주석). (1) 빈 칸 확보와 MUTEX 획득을 `semop` 한 번에 원자적으로 할 수 있다. (2) `SEM_UNDO`로 죽은 프로세스가 쥔 것을 커널이 돌려준다. 프로세스 공유 mutex는 robust 속성으로 알 수는 있지만 링 상태 복구를 직접 해야 한다. (3) `semtimedop`으로 기다림에 시간 제한을 걸 수 있다. 대가로 메시지 하나에 `semop` 시스템 콜이 보내는 쪽 2번, 받는 쪽 2번 들고, 작은 메시지에서 이 비용이 드러난다.

**Q9. 복사는 몇 번 하나? 공유 메모리면 복사가 없어야 하지 않나?**
payload는 보내는 쪽 버퍼에서 링으로 한 번, 링에서 받는 쪽 버퍼로 한 번 복사한다. 전송 계층 인터페이스(`transport.h`)가 받는 쪽 버퍼에 메시지를 통째로 담아 주기로 약속해서 복사를 없앨 수 없다. 그래도 pipe·mq는 사용자 공간 → 커널 → 사용자 공간의 복사에 시스템 콜이 조각마다 들지만, shm은 메시지 전체가 링에 들어가서 큰 메시지도 조각내지 않는다. 그래서 1MB에서 메시지 하나의 컨텍스트 스위치가 크기와 관계없이 3번이다(pipe는 66.8번).

**Q10. 링 크기는 어떻게 정했나?**
가장 큰 메시지(머리 + `MAX_PAYLOAD`, 약 1MB)를 요청 링에 4개, 응답 링에 2개 담을 수 있게 했다. 환경 변수 `OSP_SHM_CHUNK`, `OSP_SHM_REQ_CHUNKS`, `OSP_SHM_RESP_CHUNKS`로 바꿀 수 있다. 응용의 요청은 16B를 넘지 않아서 요청 링을 1개 분량(257칸)으로 줄여도 처리량이 그대로였고, 서버 최대 RSS가 0.63~0.87배로 줄었다(설계 개선 실험, N-5).

**Q11. 같은 번호의 클라이언트가 죽고 새로 붙으면 남은 응답은?**
새 클라이언트는 열 때 자기 응답 링을 MUTEX를 쥐고 비운다(`reset_my_ring`). 한계도 있다. 예전 클라이언트의 요청을 서버가 아직 처리하고 있었다면 그 응답은 비운 뒤에 들어온다. 그래서 받는 쪽은 자기가 보내지 않은 `req_id`의 응답을 버린다. 클라이언트는 세션마다 `req_id` 시작값을 `getpid() << 32`로 다르게 한다.

**Q12. 서버를 끝낼 때 공유 메모리를 쓰던 스레드는?**
세마포어를 먼저 지운다. 기다리던 `semop`이 모두 `EIDRM`으로 깨어나서, 클라이언트의 받기는 `ECONNRESET`, 보내기는 `EPIPE`로 끝난다. 그다음 공유 메모리를 쓰던 스레드 수(`srv_users`)가 0이 될 때까지 기다린 뒤 떼어 낸다. 쓰는 중인 메모리를 떼어 내 세그먼트 오류가 나는 경쟁을 막기 위해서다. T-20·T-21 시험이 끝난 뒤 자원이 남지 않는 것을 확인한다.

**Q13. 서버가 kill -9로 죽으면 공유 메모리가 남지 않나?**
남는다. 그래서 두 곳에서 지운다. 새 서버는 서버 자리(잠금 바이트 0)를 잡은 뒤 남은 자원을 지우고 새로 만든다(`remove_stale`). 기다리던 클라이언트는 서버가 죽은 것을 알면, 열 때 받아 둔 번호로만 자원을 지운다. 그 뒤에 새로 뜬 서버의 자원은 번호가 달라 건드리지 않는다.

## 클라이언트별 요청 링 (설계 개선 T7)

**Q14. 왜 만들었나?**
2단계 측정에서 shm은 클라이언트가 늘수록 요청 전송 구간이 길었다(클라이언트 4에서 29.8µs, 8에서 110.2µs. pipe 14.4, mq 8.4). 모든 클라이언트가 요청 링 하나를 MUTEX 하나로 번갈아 쓰기 때문이라고 보았다. 링을 클라이언트마다 나누면 이 다툼이 사라지는지 확인하려고 옵션(`OSP_SHM_REQ_RING=per`)으로 만들었다. 기본은 이전과 같다.

**Q15. 링이 16개면 서버는 어디서 기다리나?**
세마포어 집합 끝에 모든 요청 링의 메시지 수를 세는 `TOTAL` 세마포어 하나를 두었다. 보내는 쪽은 자기 링에 쓰고 head를 바꾼 뒤 `TOTAL`을 +1 한다. 서버 수신 스레드는 `TOTAL`에서 -1 한 뒤 지난번 다음 링부터 돌아가며(round-robin) head ≠ tail인 링에서 하나 꺼낸다. head를 먼저 바꾸고 `TOTAL`을 올리므로, `TOTAL`을 하나 얻었으면 꺼낼 메시지가 있는 링이 반드시 있다. 링마다 `MSGS`를 쓰지 않는 이유는, 서버가 꺼내지 않으면 값이 계속 커져 세마포어 최댓값(32767)을 넘기 때문이다.

**Q16. 대가는?**
요청 링이 클라이언트 수만큼 늘어 메모리가 커진다. 링 하나를 가장 큰 메시지 1개 분량으로 두어도 16개면 약 16MB다. 실제로 건드리는 것은 붙은 클라이언트의 링뿐이라 RSS는 클라이언트 수에 비례한다. 결과는 [2단계 측정 결과](../measurement/stage2.md)에 적는다.

## 측정 방법

**Q17. 측정은 어디서, 어떻게 했나?**
측정용 컴퓨터 한 대(Intel Core 5 120U, P코어 2개 4스레드 + E코어 8개, Ubuntu 26.04.1)에서 모든 IPC를 같은 스크립트로 쟀다. 터미널(Ptyxis) 새 창에서 실행하고 출력을 로그로 함께 남겼으며, 다른 새 창에서 1분마다 CPU를 많이 쓰는 다른 프로세스를 확인했다. 원자료(CSV)는 스크립트만 만들고 손으로 고치지 않는다. 표와 그림도 스크립트가 원자료에서 만든다.

**Q18. 워밍업은 왜 하나?**
처음 요청들은 페이지 폴트, 캐시, 연결 준비 비용이 섞여 느리다. 클라이언트마다 500개(`-w`)를 먼저 보내 응답을 모두 받은 뒤 측정을 시작한다. 워밍업 DRAW는 값 0으로 보내 캔버스를 바꾸지 않는다.

**Q19. 평균이 아니라 중앙값을 쓰는 이유는?**
지연 분포는 꼬리가 길다. pipe는 최대 지연이 상위 99%의 수백 배로 튀는 실행이 있어 평균이 그 몇 개에 끌려간다. 실행마다 중앙값(p50)을 내고, 여러 번 반복한 실행들의 중앙값을 다시 쓴다. 반복 사이의 흔들림은 "가운데 범위"(좋은 쪽과 나쁜 쪽 4분의 1씩 뺀 범위)로 보고, 범위가 겹치면 순위를 `≈`로 둔다.

**Q20. 조건을 번갈아 재는 이유는?**
시간에 따라 바뀌는 조건(온도, 다른 프로세스, 주파수)이 한쪽 조건에만 몰리지 않게 하려는 것이다. 설계 개선 실험은 조건마다 `REPS=2`씩 다른 폴더로 번갈아 불러 조건마다 6~10번 잰다.

**Q21. "P코어에 묶은" 실험은 왜 했나? 실제 사용 조건이 아니지 않나?**
맞다. 그래서 주 결과는 묶지 않은 본 측정(반복 20번)이고, 묶은 실험은 흔들림을 걷어 낸 순위로 덧붙인다. 묶지 않으면 클라이언트 4 이상에서 실행 사이 편차가 18~64%로 커서 순위가 갈리지 않았다. P코어(`taskset -c 0-3`)에 묶으면 편차가 2~3%로 줄고 `pipe > mq > shm`(277,392 / 260,917 / 183,124)로 갈렸다. E코어에 묶어도 순위가 같았다.

**Q22. 워커 4에서 처리량이 떨어진 이유는?**
IPC가 아니라 CPU 주파수였다. 0.1초마다 우리 스레드가 있던 CPU와 그 주파수를 표본으로 모았더니, P코어 비율은 워커 수와 관계없이 22~24%였고 평균 주파수가 워커 1에서 2,718MHz, 워커 4에서 1,374MHz였다. 스레드가 여러 코어에 흩어져 잠들고 깨기를 반복하면 코어마다 사용률이 낮아 주파수 관리자(powersave)가 주파수를 내린다. P코어에 묶으면 저하가 사라진다. governor를 performance로 바꿔 확인하는 실험(T10)은 관리자 권한이 필요해 측정하는 사람이 직접 실행한다.

**Q23. 측정 중에 다른 프로그램이 돌았다면?**
기록하고 영향을 다시 계산해 밝혔다. 2단계 본 측정 중 파일 관리자가 2초쯤 CPU를 쓴 반복을 빼고 다시 계산해도 중앙값 변화가 최대 10.1%로 실행 사이 편차보다 작았다. pipe 버퍼 교차 확인 중에는 가상머신이 떠서, 겹친 반복을 빼고 다시 계산해 변화(최대 8.9%)와 판정이 바뀌지 않은 것을 적었다.

## 결과 해석

**Q24. shm이 큰 데이터에 강한 이유는?**
메시지 전체가 링에 한 번 들어가고, 받는 쪽이 한 번 꺼낸다. pipe는 64KB 버퍼마다 양쪽이 잠들고 깨고, mq는 8KB(`msgmax`) 조각마다 시스템 콜이 든다. 1단계 1MB 처리량이 shm 9,388, mq 1,862, pipe 1,069MB/s이고, 1MB 메시지 하나의 CPU 시간이 shm 447.1, mq 762.5, pipe 1,114.6µs다.

**Q25. 그런데 작은 메시지, 클라이언트가 많을 때는 왜 shm이 가장 느린가?**
작은 메시지에서는 복사 비용이 작고 동기화 비용이 전부다. shm은 메시지 하나에 `semop`이 보내는 쪽 2번, 받는 쪽 2번이고, 모든 클라이언트가 요청 링 하나의 MUTEX를 두고 다툰다. 64B·클라이언트 8 지연이 shm 38.10, pipe 26.84, mq 23.09µs이고, 응용 클라이언트 8 처리량도 shm이 가장 낮았다(76,560). pipe는 `PIPE_BUF` 이하 요청을 잠금 없이 write 한 번으로 보내고, mq는 커널이 메시지 경계와 큐를 관리한다.

**Q26. 그러면 우리 응용에는 무엇이 맞나?**
DRAW가 90%이고 클라이언트가 여럿인 우리 응용에는 shm이 유리하지 않다. 묶지 않으면 셋의 차이가 편차 안이고, 묶으면 `pipe > mq > shm`이다. 큰 SNAPSHOT이 많을 때(DRAW 80% 이하)만 shm이 앞선다. [IPC 선택 가이드라인](../measurement/guideline.md)에 정리했다.

**Q27. pipe 버퍼를 1MB로 키웠는데 1MB 응답이 왜 더 느려졌나?**
잠들고 깨는 횟수는 예측대로 줄었다(echo 1MB에서 메시지당 자발적 문맥 교환 67.0 → 7.0). 그런데 메시지 하나의 CPU 시간이 913 → 1,003µs로 늘었다. 1MB 응답의 주 비용은 복사였고 복사가 더 비싸졌다. 후보는 쓰는 쪽이 1MB를 다 쓴 뒤에야 읽는 쪽이 읽기 시작해 두 복사가 겹치지 않는 것과, 한 번에 쌓이는 1MB가 캐시를 넘는 것이다. CPU 하나에 묶어 겹칠 수 없게 한 실험(T9)으로 둘을 가른다.

**Q28. 예측은 얼마나 맞았나?**
P1은 맞고, P2·P3·P5·P6은 부분, P4는 틀렸다. 가장 크게 어긋난 것은 shm의 작은 요청 비용을 낮게 본 것이다. 예측은 1단계에서 클라이언트마다 따로 잰 값을 썼는데, 응용에서는 모든 클라이언트가 요청 링 하나를 세마포어로 번갈아 써서 요청 전송이 pipe의 3배였다. 배치·주파수 효과도 예측에 없었다.

## 경쟁 상태와 동기화

**Q31. 그림판 하나에 여럿이 그리는 건데, 경쟁 상태가 그렇게 자주 생기나?**
캔버스 쪽은 드물다. 기본 측정 조건(한 변 16칸 사각형)에서 두 사각형이 겹칠 확률은 대략 (32/1024)², 0.1% 정도이고, 한 칸을 고치는 시간도 1µs 안쪽이라 락을 꺼도(`-l none`) 체크섬이 맞는 실행이 많다. 그러나 (1) 사각형이 크거나 여럿이 같은 곳을 칠하면 거의 반드시 터진다. 캔버스 전체 사각형을 그리는 T-13에서는 락을 끄면 매번 어긋나고 실행마다 값도 다르다. (2) 잃은 값은 되돌릴 수 없어서 드물다는 것이 락을 뺄 이유가 되지 않는다. (3) 더 자주 일어나는 경쟁은 IPC 쪽이다. 모든 클라이언트가 요청 채널 하나에 동시에 쓰고, 워커 여럿이 같은 클라이언트의 응답 채널에 동시에 쓴다. 이건 그림이 겹치든 말든 요청마다 일어난다.

**Q32. 동기화를 빼면 실제로 무슨 일이 생기나?**
[race-demo.sh](../../scripts/race-demo.sh)가 동기화를 하나씩 뺀 시연용 빌드로 같은 일을 시킨다. 컨테이너에서 미리 돌린 결과는 이렇다(측정 PC에서 다시 돌린 표를 발표에 쓴다).
- 캔버스 락을 끄면 3번 모두 체크섬이 어긋나고 세 값이 모두 다르다(갱신 유실).
- 타일 락을 읽기만 내림차순으로 잡게 하면 서버 스레드들이 락에서 서로를 기다려 클라이언트가 하나도 끝나지 않는다(교착). 평소에는 2.4초에 끝난다.
- shm 요청 링의 MUTEX를 빼면 두 클라이언트가 같은 칸에 덮어써서, 요청 160,000개 가운데 서버가 처리한 것은 약 500개이고 깨진 요청에 오류 응답이 나간다. 클라이언트는 끝나지 못한다.
- pipe 응답 FIFO의 송신 mutex를 빼면 1MB 응답 둘의 바이트가 섞여 받는 쪽이 메시지 경계를 잃고 멈춘다.

**Q33. 이 응용에서 쓴 동기화를 한 번에 말하면?**
프로세스 사이: System V 세마포어(shm 링의 MUTEX·FREE·MSGS, `SEM_UNDO`), `fcntl`/OFD 파일 잠금(pipe의 큰 요청 송신 잠금, 살아 있는지 표시), 커널이 지켜 주는 원자성(`PIPE_BUF` 이하 FIFO 쓰기, mq 메시지 경계). 스레드 사이: 타일 mutex·rwlock(오름차순으로 잡아 교착 방지), 작업 큐의 mutex와 조건변수 2개(유한 버퍼), 클라이언트별 응답 송신 mutex, 동시 요청 수를 세는 세마포어, C11 원자 변수(통계, head·tail), `sigwait` 전용 신호 스레드. 각각이 막는 것과 확인하는 시험은 [설계 명세의 공유 자원과 동기화](../design/README.md#공유-자원과-동기화)에 있다.

## 과정에 대한 질문

**Q29. 생성형 AI를 어떻게 썼나? 직접 한 것은?**
설계 토론, 코드 초안, 시험 스크립트, 측정 자동화, 문서 정리에 썼고 사용 내역은 [AI 활용 기록](../records/ai-log.md)에 모두 남겼다. AI가 낸 결과를 그대로 믿지 않도록 정한 규칙이 있다. 원자료는 스크립트만 만들고, 모든 변경은 `make test`(PASS/FAIL)와 ThreadSanitizer, 세 IPC 체크섬 비교를 통과해야 병합하며, AI가 만든 측정 오염(가상머신)도 기록하고 다시 계산했다. 설계 결정(세마포어 선택, 링 크기, 측정 방법)은 이 문서의 답처럼 직접 설명할 수 있어야 한다는 기준으로 검토했다.

**Q30. 경쟁 상태가 없다는 것을 어떻게 확인했나?**
설계로 막고 시험으로 확인했다. 설계: 링의 head는 MUTEX, tail은 받는 쪽 하나, 서버 캔버스는 전역·타일 락, 클라이언트 공유 상태는 mutex. 시험: 서버 종료 체크섬을 스레드 하나로 다시 그린 검증기 값과 비교하고(T-12, 세 IPC가 같은 값), 락을 끄면(`-l none`) 체크섬이 어긋나는 것을 관찰하고(T-13), ThreadSanitizer로 빌드해 경고가 없는지 본다.

## 직접 해 보기

발표 전에 한 번씩 해 보고, 답이 어느 코드에 해당하는지 짚어 본다.

```bash
make
./bin/server_shm &                      # 서버
ipcs -m -s | grep 0x0000ea7             # Q1: 세그먼트 2개, 세마포어 집합 2개 (요청 집합은 3개, 응답 집합은 48개)
for i in 0 1 2 3; do ./bin/client_shm -i $i -f 16 & done; wait
kill -INT %1; wait                      # 서버가 checksum 을 찍는다
./bin/verify -c 4                       # Q30: 같은 checksum
ipcs -m -s | grep -c 0x0000ea7          # Q12: 0

OSP_SHM_REQ_RING=per ./bin/server_shm & # Q15: 요청 집합이 49개(16 × 3 + TOTAL)가 된다
ipcs -s | grep 0x0000ea7
kill -INT %1; wait

./bin/server_shm &                      # Q6: 보내는 도중 kill -9
./bin/client_shm -i 0 -n 1000000 -f 16 & sleep 1; kill -9 $!
./bin/client_shm -i 1 -n 1000           # 다른 클라이언트는 멈추지 않고 끝난다
./bin/client_shm -i 0 -n 1000           # 죽은 클라이언트의 번호도 다시 쓸 수 있다 (Q11)
kill -INT %1; wait

scripts/race-demo.sh                    # Q32: 동기화를 하나씩 뺀 빌드와 평소 빌드 (약 2분, 서버를 띄워 두지 않은 상태에서)
```

- 코드에서 찾아볼 곳: `ring_send`(Q2·Q3·Q6), `sem_ops`(Q7), `tp_recv_req`(Q15), `tp_server_close`(Q12), `reset_my_ring`(Q11), `remove_stale`(Q13), `lock_rect`(canvas.c, Q31·Q32).
