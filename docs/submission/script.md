# 발표 대본 — 공유 캔버스 서버

발표자료(`presentation.pptx`)의 슬라이드 노트와 같다. 동영상은 이 순서대로 슬라이드를 넘기며 읽고, 5.2절 데모 시나리오를 10번 슬라이드 뒤에 넣는다. 수치는 모두 최종보고서와 같다.

## 1. 

안녕하세요, UNIX시스템프로그래밍 2팀입니다. 저희는 공유 캔버스 서버를 pipe, message queue, shared memory 세 가지 IPC로 만들고, 작은 명령과 큰 데이터가 섞인 통신에서 어떤 IPC가 언제 유리한지 직접 측정으로 답했습니다.

## 2. 

응용은 공유 캔버스 서버입니다. 클라이언트는 작은 그리기 명령을 자주 보내고, 가끔 캔버스 일부나 전체를 받아 갑니다. 그래서 수십 바이트 메시지와 1메가바이트 메시지가 한 채널에 섞입니다. 리눅스 화면 시스템도 같은 문제 때문에 공유 메모리 통로를 따로 두었습니다. 저희는 이 상황에서 세 IPC를 비교하는 것을 목표로 했습니다.

## 3. 

요구사항은 정합성, 교착과 섞임 없음, 측정 가능성이 핵심입니다. 그리기를 더하기로 정의해서 실행 순서와 관계없이 최종 체크섬이 정답과 같아야 하고, 이것으로 경쟁 상태를 검사합니다. 과제 조건인 스레드 수, 자원 정리는 make test의 78개 항목이 모두 자동으로 확인합니다.

## 4. 

1단계는 같은 크기로 돌려주는 echo 벤치마크로, 7가지 크기와 클라이언트 1, 2, 4, 8개를 20번씩, 모두 4,480번 쟀습니다. 16킬로바이트 이하에서는 세 IPC의 지연이 실행 사이의 흔들림보다 차이가 작아 구분되지 않습니다. 64킬로바이트부터는 pipe가 2~3배 느려집니다. pipe는 64킬로바이트 버퍼가 찰 때마다 양쪽이 잠들고 깨기 때문이고, 1메가바이트에서 컨텍스트 스위치가 66.8번으로 계산과 맞았습니다. 작은 메시지의 흔들림은 P코어와 E코어 배치 때문인 것을 코어를 묶는 실험으로 확인했습니다.

## 5. 

처리량은 4킬로바이트까지 mq가, 16킬로바이트부터는 shm이 크게 앞섭니다. 64킬로바이트에서 shm이 mq의 4.4배입니다. 다만 작은 메시지를 클라이언트 여럿이 보내면 shm이 가장 느려졌습니다. 모든 클라이언트가 요청 링 하나를 세마포어로 번갈아 쓰기 때문이고, 이것은 2단계에서 구간별 시간으로 확인했습니다.

## 6. 

워크로드는 요청이 40바이트 이하, 응답만 큰 비대칭입니다. 기준 조건은 그리기 90퍼센트, 클라이언트 4개입니다. 서버와 클라이언트를 쓰기 전인 11월 18일에 1단계 값으로 여섯 가지 예측을 숫자로 커밋했습니다. 핵심은 shm이 큰 응답에서는 빠르지만 요청의 90퍼센트인 작은 요청에서 잃어서, 혼합 워크로드에서는 크게 앞서지 않는다는 것이었습니다.

## 7. 

구조입니다. 클라이언트의 송신 스레드가 공용 요청 채널로 보내면 서버 수신 스레드가 작업 큐에 넣고, 워커가 캔버스를 처리해 클라이언트별 응답 채널로 보냅니다. 세 버전에서 달라지는 것은 파란 두 채널뿐이고 나머지는 같은 코드입니다. 그래서 차이가 IPC에서만 나옵니다.

## 8. 

공유 자원마다 동기화 기법을 정했습니다. 캔버스는 타일 락이고, 여러 타일은 항상 번호 오름차순으로 잡아 교착을 막습니다. shm 링은 빈 칸과 뮤텍스 세마포어를 semop 한 번에 얻어서 기다리는 동안 아무것도 쥐지 않습니다. 또 워커는 락 안에서 복사만 하고 락 밖에서 응답을 보냅니다.

## 9. 

서버와 클라이언트는 transport.h의 함수 9개만 부르고, 어떤 IPC인지는 링크할 때 정해집니다. 큰 응답은 pipe는 writev를 반복하고, mq는 8킬로바이트 조각으로 나눠 재조립하고, shm은 링에 한 번 복사합니다. make test는 체크섬 일치와 자원 정리를 포함해 대화형 draw, 멀티 방, 256클라이언트 확장 검증까지 78개 항목을 자동으로 확인하고 모두 통과합니다.

## 10. 

실행 화면입니다. shm 서버에 클라이언트 4개가 2만 개씩 요청한 뒤 서버를 끝내면 체크섬이 검증기의 정답과 같습니다. pipe와 mq도 같은 체크섬이 나옵니다. 오른쪽은 락을 끈 실행으로, 같은 칸에 동시에 더하다 갱신이 사라져 체크섬이 어긋납니다. 끝난 뒤 ipcs에 남은 자원은 없습니다.

## 11. 

예측과 비교하면 하나는 맞고, 넷은 부분적으로, 하나는 틀렸습니다. 가장 크게 틀린 P4는 기준 혼합 처리량으로, 흔들림을 걷어 내면 shm이 가장 낮았습니다. 구간별 시간을 보면 shm의 요청 전송이 26.2마이크로초로 pipe의 3배입니다. 1단계는 클라이언트마다 따로 잰 값이라 요청 링 하나를 다투는 비용이 예측에 없었습니다. 또 pipe와 mq는 서버 작업 큐에서 400마이크로초 안팎을 기다려, 서버 안쪽 비용이 IPC 비용보다 컸습니다.

## 12. 

워커 4개에서 pipe와 mq의 처리량이 20번 모두 떨어졌습니다. 코어에 묶는 실험과 0.1초마다 스레드 위치와 주파수를 모은 결과, P코어 비율은 같고 주파수가 워커 1의 절반이었습니다. 스레드가 흩어져 코어가 덜 바쁘면 주파수 관리자가 주파수를 내리는 것입니다. P코어에 묶으면 저하가 사라지고 편차도 2~3퍼센트로 줄었습니다. 그래서 이 저하는 IPC나 서버 설계가 아니라 측정용 컴퓨터의 특성으로 결론 내렸습니다.

## 13. 

설계 개선은 두 가지입니다. 왼쪽은 pipe 버퍼를 키운 것입니다. 1메가바이트 응답이 빨라질 것으로 예상했지만 오히려 1.4~1.6배 느려졌고, 다른 시간대와 echo 벤치마크로 다시 재도 같았습니다. 잠드는 횟수는 10분의 1로 줄었지만 메시지당 CPU 시간이 늘어서, 1메가바이트의 비용은 잠들기가 아니라 복사였습니다. 오른쪽은 메모리 절감으로, 요청이 작으니 shm 요청 링을 줄였더니 처리량 손해 없이 최대 메모리가 줄었습니다.

## 14. 

측정을 종합한 가이드라인입니다. 16킬로바이트 이하에서 지연만 본다면 어떤 IPC든 차이가 흔들림보다 작습니다. 작은 메시지를 많이 보내면 mq, 64킬로바이트 이상의 큰 데이터는 shm입니다. 하지만 클라이언트가 많고 메시지가 작으면 shm은 오히려 불리합니다. 그래서 그리기가 90퍼센트인 저희 응용에는 pipe나 mq가 맞고, shm은 큰 조회가 많을 때만 앞섰습니다. 그리고 이 컴퓨터에서는 IPC 차이보다 CPU 배치와 주파수의 영향이 컸기 때문에, 실제로 돌릴 컴퓨터에서 반복해서 재고 고르는 것이 중요합니다.

## 15. 

역할은 IPC를 하나씩 맡고, 쉬운 IPC에 무거운 공통 코드를 붙여 양을 맞췄습니다. 작업은 GitHub 이슈와 PR로 나눴고, 모든 PR은 make test를 통과해야 병합되게 했습니다. 예측을 먼저 커밋하는 규칙도 자동으로 검사했습니다.

## 16. 

정리하면, shm이 가장 빠르다는 일반론은 큰 메시지에서만 맞았고, 작은 요청이 대부분인 저희 응용에서는 shm이 가장 느렸습니다. 또 1단계 echo만으로는 응용을 예측할 수 없었습니다. AI는 분석부터 문서까지 썼지만 결과는 모두 측정과 시험으로 확인했고, AI가 틀린 사례 11건과 AI 생성 코드 결함 22건을 기록하고 바로잡았습니다. 예를 들어 mq가 조각마다 송수신을 교대한다는 설명은 CPU가 하나일 때만 맞았고, pipe 버퍼를 키우면 빨라진다는 제안은 1메가바이트에서 오히려 느려졌습니다. 감사합니다.
