# 발표 대본 — 다중 그림판 공유 캔버스 서버 (2팀 Canvas)

발표자료(`발표자료.pptx`) 슬라이드 16장의 대본이다. 각 슬라이드의 발표자 노트에도 같은 내용이 들어 있다. 전체 약 6,120자(공백 제외)로, 보통 속도(분당 350~400자)로 읽으면 약 15~17분이다. 실행 결과 슬라이드에서 데모 영상(`데모영상.mp4`, 2분 27초)을 틀면 그만큼 늘어난다.

## 1. 표지 — 다중 그림판 공유 캔버스 서버

안녕하세요, UNIX시스템프로그래밍 설계과제 2팀 Canvas입니다. 저희는 여러 사람이 한 컴퓨터 안에서 같은 그림판에 동시에 그리는 '다중 그림판 공유 캔버스 서버'를 만들었습니다. 같은 응용을 pipe, message queue, shared memory 세 가지 IPC로 각각 구현했고, 1단계 기초 측정으로 세운 예측이 실제 응용에서도 맞는지 확인했습니다. 팀장 이동건이 shared memory, 김병수가 pipe, 오현근이 message queue 버전을 맡았습니다. 발표는 문제 정의, 1단계 측정, 예측, 설계와 구현, 성능 분석, 그리고 결론 순서로 진행하겠습니다.

## 2. 문제 정의 — 여러 사람이 한 그림판에 동시에 그린다

먼저 응용입니다. 서버는 1024 곱하기 1024칸짜리 그림판 8개를 가지고 있고, 클라이언트는 최대 1024개 프로세스가 동시에 붙습니다. 요청은 두 가지입니다. DRAW는 사각형 칸에 값을 더하는 그리기 명령으로 요청 40바이트, 응답 56바이트이고 전체 요청의 90%입니다. SNAPSHOT은 지금 보고 있는 영역을 받아 오는 요청으로 응답이 최대 65,592바이트, 즉 약 64KB입니다. 오른쪽 그림처럼 요청은 많은 클라이언트에서 서버 하나로 모이는 N대1이고 작습니다. 반대로 응답은 서버에서 각 클라이언트로 흩어지는 1대N이고, 응답 바이트의 99.2%가 64KB SNAPSHOT입니다. 작은 N대1 통신과 큰 1대N 통신이 한 응용에 같이 있기 때문에, 어떤 IPC를 쓰느냐에 따라, 특히 채널을 어떻게 나누느냐에 따라 성능이 크게 달라질 것으로 봤습니다.

## 3. 요구사항 — 1024명이 함께 그려도 한 프레임 안에

요구사항을 숫자로 정했습니다. 세 버전 모두 클라이언트 1024개까지 동작해야 하고, 사람 1024명이 동시에 그리는 부하, 즉 초당 약 68,000개 요청에서 DRAW 왕복 지연의 상위 99%가 60Hz 화면 한 프레임인 16.7ms 안에 들어와야 합니다. 메모리는 클라이언트 하나당 IPC 버퍼 160KB 이하로 제한했습니다. 과제 제약도 지켰습니다. 서버는 스레드 7개(mq는 감시 스레드를 더해 8개), 클라이언트는 4개로 모든 프로세스가 3개 이상이고, make로 버전별 또는 한 번에 컴파일합니다. 종료하면 우리 key 60020부터 60029와 FIFO가 하나도 남지 않고, 모든 측정 실행에서 서버의 그림판 체크섬이 검증기의 정답과 같아 경쟁 상태가 없음을 확인했습니다.

## 4. 1단계 기초 측정 — 64KB부터 pipe만 뒤처진다

1단계 기초 측정입니다. 측정은 모두 같은 PC 한 대에서 했습니다. Intel Core 5 120U, 논리 CPU 12개, Ubuntu 26.04 네이티브 환경입니다. echo 방식의 왕복 지연과 동시 요청 16개일 때의 처리량을 메시지 크기 7단계, 클라이언트 1, 2, 4, 8개, IPC 네 종류로 쟀고 조건마다 20번 반복해 중앙값을 썼습니다. 그래프는 클라이언트 1개의 왕복 지연 중앙값이고 세로축은 로그 눈금입니다. 16KB까지는 세 선이 거의 겹치지만, 64KB부터 빨간 pipe만 위로 벌어집니다. 64KB에서 pipe는 82마이크로초, mq와 shm은 약 35마이크로초였습니다.

## 5. 1단계 결과 해석 — 복사 횟수와 잠드는 횟수가 갈랐다

이 결과를 동작 원리로 해석했습니다. 16KB 이하에서는 세 IPC가 구분되지 않습니다. 64바이트 중앙값이 10마이크로초 안팎으로 같고, 실행 사이 편차가 IPC 사이 차이보다 컸습니다. 시스템 콜과 스레드를 깨우는 비용이 비슷하기 때문입니다. 64KB 이상에서는 mq와 shm이 pipe보다 약 2.4배 빨랐습니다. 메시지 하나당 자발적 문맥 교환이 pipe는 7번인데 shm은 3번이었습니다. pipe는 64KB 파이프 버퍼를 넘는 메시지를 여러 번에 나눠 쓰면서 그때마다 잠들기 때문입니다. 반대로 클라이언트 8개, 64바이트에서는 shm이 38마이크로초로 가장 느렸는데, 모든 클라이언트가 요청 링 하나를 MUTEX 세마포어로 다투기 때문입니다. 이 결과가 다음 예측의 근거가 됩니다.

## 6. 워크로드 명세와 성능 예측 — 사람 한 명의 그리기를 기준으로 예측했다

응용을 구현하기 전에 워크로드와 예측을 먼저 커밋했습니다. 사람 한 명이 마우스로 그리면 초당 DRAW 60개와 SNAPSHOT 6.7개, 합쳐 67개의 요청을 보낸다고 보고, 비율을 DRAW 90 대 SNAPSHOT 10으로 정했습니다. 오른쪽이 예측 여덟 개입니다. 요청이 작은 클라이언트 1개의 DRAW는 세 IPC가 비슷할 것, 64KB SNAPSHOT은 mq와 shm이 pipe보다 1.7배 빠를 것, 처리량은 shm이 가장 높을 것으로 봤습니다. 클라이언트가 늘면 shm은 요청 링 경쟁, mq는 응답 큐 하나를 나눠 쓰는 구조 때문에 무너지고, 256개 이상에서는 클라이언트별 FIFO를 쓰는 pipe가 1위가 될 것이라고 예측했습니다. 판정은 1단계와 같은 규칙으로, 실행 사이 흔들림보다 작은 차이는 같은 순위로 묶었습니다.

## 7. 소프트웨어 설계도 — 세 버전은 전송 계층만 다르다

설계도입니다. 세 버전은 가운데 전송 계층 파일 하나만 다르고, 서버, 부하 클라이언트, 그리기 클라이언트, 실행기, 검증기는 모두 같은 코드입니다. 그래서 측정 차이는 IPC에서만 나옵니다. pipe 버전은 요청 FIFO 하나에 모든 클라이언트가 40바이트 이하 요청을 원자적으로 쓰고, 응답은 클라이언트마다 FIFO를 따로 둡니다. mq 버전은 요청 큐와 응답 큐를 하나씩 두고 mtype으로 클라이언트를 구분하며, 64KB 응답은 8KB 조각 9개로 나눠 보냅니다. shm 버전은 공유 메모리 링 버퍼에 System V 세마포어로 동기화합니다. 서버 안에서는 수신 스레드가 요청을 받아 작업 큐에 넣고, 워커 4개가 꺼내 그림판에 그린 뒤 응답합니다. 요청이 지나가는 각 지점에서 시각을 찍어 어디서 시간이 걸리는지 나눠 볼 수 있게 했습니다.

## 8. 스레드 설계 — 모든 프로세스가 스레드 3개 이상

스레드 설계입니다. 서버는 main, 수신 스레드 1개, 워커 4개, 관리 스레드 1개로 모두 7개입니다. mq 버전은 죽은 클라이언트를 치우는 감시 스레드가 하나 더 있습니다. 수신과 처리를 나눈 이유가 있습니다. 요청 채널은 한 스레드가 차례로 읽어야 합니다. 특히 pipe는 바이트 스트림이라 여러 스레드가 읽으면 메시지가 섞입니다. 반면 처리는 그림판과 타일마다 동시에 할 수 있습니다. 관리 스레드는 sigwait로 신호를 받아 종료와 측정 시작·끝 표시를 맡습니다. 부하 클라이언트는 송신, 수신, 신호 스레드로 나눠, 동시 요청 수만큼의 빈 칸을 세마포어로 관리하며 보내고 받습니다. 그리기 클라이언트는 마우스 입력, 수신, 화면 갱신, 신호 스레드로 동작하고, 실행기는 클라이언트 1024개를 띄워 신호 하나로 동시에 시작시킵니다.

## 9. 공유 자원과 동기화 — 경쟁은 락 순서와 원자적 넘김으로 막았다

공유 자원과 동기화입니다. 그림판은 64칸 타일마다 rwlock을 둬서 DRAW는 쓰기 락, SNAPSHOT은 읽기 락을 잡습니다. 한 요청이 여러 타일을 잡을 때는 항상 행 우선 오름차순으로만 잡아 기다림의 고리, 즉 교착이 생기지 않습니다. 작업 큐는 mutex와 조건변수 두 개로 만든 생산자-소비자 구조이고, 통계는 워커별 원자 변수로 둬 캐시 줄 경쟁을 피했습니다. shm 링은 빈 칸과 MUTEX를 semop 한 번에 얻고 SEM_UNDO로 죽은 프로세스가 쥔 것을 커널이 돌려주게 했습니다. 그리고 CI에서 한 번 실패한 시험의 원인을 찾다가 pipe가 남은 FIFO를 지우고 다시 만드는 사이의 TOCTOU 경쟁을 발견했습니다. CPU 부하를 걸었을 때 서버 둘을 동시에 띄우면 150쌍 중 21쌍에서 둘 다 뜨는 것을 재현했고, flock 시작 잠금으로 묶어 0쌍으로 고쳤습니다. 락을 끈 서버만 체크섬이 어긋나고 ThreadSanitizer 보고는 0건이었습니다.

## 10. 소스코드 주요 부분 — 교착을 막는 락 순서와 shm 송신

핵심 코드 두 부분입니다. 왼쪽은 그림판 타일 락입니다. 요청이 덮는 타일 범위를 구한 뒤 행 우선 오름차순으로 락을 잡습니다. 모든 스레드가 같은 순서로 잡기 때문에 교착이 생기지 않고, DRAW는 쓰기 락, SNAPSHOT은 읽기 락이라 읽기끼리는 막지 않습니다. 오른쪽은 shm 링 버퍼의 송신입니다. 빈 칸 k개와 MUTEX를 semop 한 번으로 함께 얻어, 기다리는 동안 아무것도 쥐고 있지 않게 했습니다. 데이터는 커널을 거치지 않고 링에 바로 복사하고, head를 release로 갱신한 다음 메시지 세마포어를 올려 받는 쪽을 깨웁니다. 전송 계층 함수만 버전마다 다르고 나머지 약 7,500줄은 공통입니다.

## 11. 실행 결과 — 그리기 클라이언트 둘과 봇 1022개가 함께 그린다

실행 결과입니다. 데모는 측정에 쓴 PC의 실제 화면을 녹화했고, 터미널 창 네 개에 서버, 그리기 클라이언트 두 개, 명령 창을 띄웠습니다. 먼저 make로 빌드하고 make test로 시험이 모두 통과하는 것을 확인했습니다. 서버를 띄우고 그리기 클라이언트 두 개를 같은 그림판에 접속시킨 뒤 한쪽에서 마우스로 IPC라고 쓰면, 오른쪽 위 그림처럼 다른 쪽 화면에도 바로 나타납니다. 왼쪽 큰 화면은 여기에 실행기로 봇 1022개를 더해 접속이 1024개가 된 모습입니다. 봇들이 그린 사각형이 계속 더해지고, 오른쪽 아래 명령 창에서는 서버가 만든 공유 메모리 두 개와 세마포어 집합 두 개를 ipcs로 확인했습니다. 서버를 Ctrl+C로 끝내면 그림판별 체크섬을 출력하고 IPC 자원을 모두 지웁니다. 종료 뒤 ipcs에는 우리 key가 하나도 남지 않았습니다. 마지막으로 데모 점검 스크립트로 세 버전 모두 클라이언트 1024개를 돌려, 서버 체크섬이 검증기 정답과 같고 남은 자원이 없음을 보였습니다.

## 12. 예측 대비 실측 — 예측 8개 가운데 7개 부분 일치, 1개 불일치

예측과 실측을 비교한 표입니다. 판정은 3장에서 정한 규칙 그대로, 순위와 수치 범위가 모두 맞으면 일치, 순위는 맞지만 범위를 벗어나거나 일부 조건에서만 맞으면 부분 일치, 순위가 다르면 불일치로 했습니다. 여덟 개 가운데 부분 일치가 일곱, 불일치가 하나입니다. 클라이언트 하나의 DRAW는 세 IPC가 13.1에서 16.1마이크로초로 구분되지 않았고, 64KB SNAPSHOT은 pipe만 2.3배 느렸습니다. 1단계에서 본 복사 횟수의 차이가 응용에서도 그대로 나온 것입니다. 순위가 틀린 곳은 P3 처리량입니다. shm이 1위일 것으로 봤지만 mq가 1위였고, shm은 전송 계층만의 상한의 50%에 그쳤습니다. 클라이언트가 많아지는 P4와 P5는 큰 그림은 맞았지만, shm은 16개부터 3.7만에서 5.9만 요청에 멈췄고 mq는 1024개에서 크게 무너졌습니다. 사람 1024명 속도의 목표 부하에서는 처음 설계에서 pipe 30번 모두 DRAW 상위 99%가 한 프레임 안에 들어왔습니다. 틀린 곳은 모두 동기화, 즉 여러 스레드와 프로세스가 같은 것을 어떻게 기다리고 깨우는지에서 나왔습니다. 1단계 echo에는 워커도, 클라이언트 수백 개도 없었기 때문에 볼 수 없던 요인입니다.

## 13. 원인 분석 — 무너진 곳은 IPC가 아니라 기다리는 방식이었다

왼쪽은 처음 설계에서 클라이언트 수에 따른 처리량입니다. 클라이언트가 16개를 넘으면 pipe가 1위가 되고, shm은 16개부터, mq는 256개부터 무너집니다. 원인은 IPC 자체가 아니라 여러 프로세스가 같은 것을 기다리는 방식이었습니다. shm은 늘어난 시간이 모두 요청 전송입니다. 모든 클라이언트가 요청 링 하나의 MUTEX 세마포어를 잡아야 보낼 수 있는데, System V 세마포어는 기다리던 프로세스에 차례로 넘겨주기 때문에 칸 하나를 넣을 때마다 잠든 프로세스가 깨어날 때까지 링이 멈춥니다. 띄운 요청 수는 그대로 두고 기다리는 프로세스 수만 64개로 줄이면 처리량이 2.2배가 되어 이것을 확인했습니다. mq는 응답 큐 하나를 1024개가 나눠 씁니다. 응답 큐를 네 개로 나누면 9.0배가 되지만, 여덟 개로 나누자 30번 중 12번은 가득 찬 요청 큐가 메시지 하나가 빠질 때마다 송신자를 모두 깨우는 현상으로 무너졌습니다. 클라이언트 하나에서 shm이 mq에 진 이유는 처음에 워커 경쟁으로 추정했지만, 워커 수와 응답 링 크기만 바꾼 실험에서 순위가 그대로여서 두 추정 모두 틀렸습니다. 요청 종류만 바꾸자 작은 요청에서 shm이 mq의 0.38배라는 것이 드러났습니다. 세마포어 연산이 요청 하나에 여덟 번이기 때문입니다. 마지막으로 pipe가 64KB 응답에서 느린 이유는 응답 FIFO 용량이 가장 큰 응답보다 56바이트 작아, 워커가 FIFO에서 클라이언트를 기다리기 때문이었습니다. FIFO만 128KB로 키우면 SNAPSHOT만 보낼 때 처리량이 27,865에서 43,171 요청으로 늘었습니다.

## 14. 설계 개선 전후 — 1024개 처리량 mq 13.6배, shm 6.3배, pipe 1.10배

원인을 그대로 고쳤습니다. 세 개선 모두 서버 환경 변수로 켜고 끄기 때문에 같은 실행 파일로 전후를 비교했고, 세 IPC를 같은 조건 목록으로 한 반복 안에서 처음 설계와 번갈아 쟀습니다. mq는 응답 큐를 8개로 나누고 요청 큐 앞에 입장 제한을 두었습니다. 입장 제한은 요청 큐의 빈 자리 수를 값으로 둔 세마포어로, 유한 버퍼의 빈 칸 세마포어와 같습니다. shm은 요청 링을 클라이언트마다 하나씩 나눠 MUTEX를 없앴습니다. pipe는 64KB 응답을 보낼 때 응답 FIFO를 128KB로 키우고, 사용자별 파이프 한도 때문에 키울 수 없는 1024개에서는 워커가 못 쓴 나머지를 송신 스레드에 맡겨 워커가 클라이언트를 기다리지 않게 했습니다. 세 개선 모두 클라이언트당 버퍼 160KB라는 같은 한도 안에 있습니다. 클라이언트 1024개 처리량은 mq 15,066에서 205,011, shm 41,383에서 259,985, pipe 238,626에서 262,018 요청이 되었습니다. 속도도 함께 봤습니다. 1024개의 상위 99% 지연은 mq 147.5ms에서 7.5ms, shm 43.4ms에서 5.5ms로 줄었고, pipe는 5.2ms에서 5.8ms가 됐습니다. pipe는 처음부터 무너지는 곳이 없어 개선 폭이 작습니다. shm에도 대가가 있었습니다. 클라이언트 하나가 요청을 16개씩 띄우면 0.94배로 느려졌습니다. 서버가 요청을 받을 때마다 클라이언트별 링 1,024개를 차례로 훑기 때문인데, 받을 클라이언트 수를 16으로 줄이면 221,011에서 237,764 요청으로 공용 링과 거의 같아져 이것을 확인했습니다. 사람 1024명 속도의 목표 부하에서는 개선 뒤 pipe·mq·shm 30번 모두 한 프레임 안에 들어왔습니다. 정리하면 우리 응용에는 pipe를 고릅니다. 처음 설계로도 목표 부하를 통과했고, 개선한 세 IPC 가운데서도 목표 부하의 DRAW 상위 99%가 378µs로 가장 짧았습니다. mq와 shm은 개선해야 이 응용에 쓸 수 있습니다. 클라이언트가 적고 64KB 응답이 잦으면 복사가 한 번인 mq나 shm, 작은 요청만 오가면 가장 단순한 pipe면 충분합니다.

## 15. 팀워크 — IPC 하나씩, 공통 코드는 무게에 맞춰 나눴다

팀워크입니다. IPC는 한 사람이 하나씩 맡고, 공통 코드는 IPC의 무게에 맞춰 나눴습니다. 이동건은 shared memory 전송 계층과 실행기·측정 도구·1단계 벤치마크를 맡았고, 2단계 재수행에서 구현과 측정, 설계 개선을 이끌었습니다. 김병수는 pipe 전송 계층과 그림판·서버의 첫 구현, 재접속과 종료 결함 수정을 맡았습니다. 오현근은 message queue 전송 계층과 클라이언트·요청 생성기·검증기의 첫 구현, 그리고 저장소 전체 시험으로 결함 여섯 건을 찾아 고쳤습니다. 모든 변경은 이슈를 만들고 PR로 올려 make test를 통과한 뒤에 합쳤고, 측정은 과제 조건대로 PC 한 대에서만 했습니다. 이 과제에 들인 시간은 이동건 66시간, 김병수 41시간, 오현근 44시간, 모두 151시간입니다.

## 16. 결론 및 AI 활용 — 측정이 예측을 고쳤고, 원인을 찾아 설계를 바꿨다

결론입니다. 1단계에서 본 메시지 하나의 비용, 즉 작은 메시지는 같고 64KB는 pipe만 느리다는 결론은 응용에서도 그대로 맞았습니다. 하지만 클라이언트가 많아지자 IPC 자체보다 여러 프로세스가 같은 것을 어떻게 기다리는지가 성능을 갈랐고, 예측이 틀린 곳은 모두 여기서 나왔습니다. 원인은 추측으로 끝내지 않고 요인 하나만 바꾼 실험으로 확인했고, 그 과정에서 우리의 추정 세 가지가 틀렸다는 것도 확인했습니다. 그리고 세 IPC 모두 기다리는 곳을 없애는 설계 개선을 했습니다. AI는 Claude를 기획부터 문서까지 에이전트 방식으로 썼습니다. AI가 틀린 사례도 여럿 있었습니다. 처리량은 shm이 1위라는 예측과 그 원인을 워커 경쟁으로 본 추정, 응답 큐만 나누면 mq가 살아난다는 판단, 그리고 pipe 개선을 다른 IPC와 다른 서버 설정과 메모리 한도로 재기 시작한 것입니다. 마지막은 저희가 측정 조건이 같아야 하지 않느냐고 두 번 물어 찾아냈고, 그 측정을 버리고 세 IPC를 같은 조건으로 다시 쟀습니다. 들어 주셔서 감사합니다.
