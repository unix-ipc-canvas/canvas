# 이슈·PR 작성 규칙 — 공유 캔버스 서버

[문서 안내](../README.md#관련-문서)

작업은 이슈 → 브랜치 → 커밋 → PR → 병합 순서로 한다. 작성은 [이슈 템플릿](../.github/ISSUE_TEMPLATE)·[PR 템플릿](../.github/PULL_REQUEST_TEMPLATE.md)에서 시작한다. 요구사항·문서의 관리 원칙은 [작업 지침](../AGENTS.md)을 따른다.

## 이슈

- 제목은 `[Feature] 요약`, `[Task] 요약`, `[Bug] 요약`, `[Experiment] 요약` 중 하나로 작성한다. 각각 기능 구현, 문서·빌드·측정 실행 등 기타 작업, 오류, 원인 확인 실험과 개선 전후 비교에 사용한다.
- 예: `[Feature] pipe 전송 계층 구현`, `[Task] 1단계 메시지 크기별 측정`, `[Bug] 종료 후 메시지 큐가 남음`, `[Experiment] 전역 락이 SNAPSHOT 지연의 원인인가`.
- 본문에는 할 일과 끝났다는 기준을 적는다. 버그는 재현 방법·기대한 동작·실제 동작·실행 환경을 함께 적는다.
- 실험은 가설, 바꾼 옵션 하나, 고정한 조건, 결과를 적는다. 보고서 6.4절과 6.5절의 근거가 된다.
- 관련 요구사항 번호(F-2, C-5 등)가 있으면 적고, 해당하지 않는 템플릿 항목은 삭제한다.
- 라벨은 타입 1개(`feat`, `fix`, `exp` 등)와 범위 1개(`pipe`, `mq`, `shm`, `server`, `client`, `bench`)를 붙인다.

## 브랜치

- 이름은 `type/이슈번호-짧은-설명`으로 짓는다. 예: `feat/12-pipe-transport`, `fix/20-mq-cleanup`, `docs/7-prediction`.
- `main`에 바로 푸시하지 않는다.

## 커밋

- 제목은 `type: 요약`으로 작성한다. type은 영어 소문자, 요약은 한국어로 50자 안팎, 마침표 없이 쓴다.
- type은 `feat`(기능), `fix`(버그 수정), `perf`(성능 개선), `refactor`(동작 변경 없는 구조 개선), `test`(검증 코드), `exp`(측정 실행과 원자료 추가), `docs`(문서), `build`(Makefile·CI), `chore`(설정·도구 등 기타 작업)를 사용한다.
- 예: `feat: FIFO 요청 채널 구현`, `fix: 종료 시 메시지 큐가 남는 문제 수정`, `exp: 1단계 메시지 크기별 지연 측정`.
- 한 커밋에는 한 가지 일만 담는다. 본문이 필요하면 한 줄 띄우고 이유를 쓴다.
- `exp`는 표준 타입이 아니고 이 프로젝트에서만 쓴다. 측정 커밋을 따로 찾기 쉽게 하려는 것이다.
- 처음 한 번 `git config commit.template .gitmessage`를 실행하면 커밋할 때 안내가 뜬다.

## PR

- 제목은 커밋과 같은 `type: 요약`으로 작성한다. 예: `feat: pipe 전송 계층 구현`.
- 하나의 목적을 다루고, 본문에 변경 이유·내용과 검증 방법·결과를 적는다. 검사를 실행하지 못했다면 이유를 적는다.
- 이슈를 해결하면 `Fixes #123`, 참고만 하면 `Refs #123`으로 연결한다.
- 필요한 문서 변경을 함께 넣고, 해당하지 않는 템플릿 항목은 삭제한다.
- 합치기 전에 CI가 통과해야 하고, 다른 팀원 1명이 확인한다. `include/`의 두 헤더를 바꾸는 PR은 세 사람이 모두 확인한다.

## 넣지 않는 것

커밋 메시지, PR, 이슈에 AI 도구의 서명(`Co-Authored-By`, 생성 도구 표시, 세션 링크)을 넣지 않는다. AI 사용 사실은 [AI 활용 기록](records/ai-log.md)에 적는다.
