# 커밋·이슈·PR 작성 규칙

작업은 이슈 → 브랜치 → 커밋 → PR → 병합 순서로 한다. 작업 전반의 원칙은 [작업 지침](AGENTS.md)에 있다.

## 이슈

제목 앞에 종류를 대괄호로 붙인다. 템플릿 4종 중 하나를 고르면 자동으로 붙는다.

| 종류 | 언제 | 예 |
| --- | --- | --- |
| `[Feature]` | 기능 구현 | `[Feature] pipe 전송 계층 구현` |
| `[Task]` | 문서, 빌드, 측정 실행, 정리 | `[Task] 1단계 메시지 크기별 측정` |
| `[Bug]` | 잘못된 동작 | `[Bug] 종료 후 메시지 큐가 남음` |
| `[Experiment]` | 원인 확인 실험, 개선 전후 비교 | `[Experiment] 전역 락이 SNAPSHOT 지연의 원인인가` |

- 한 이슈에는 한 가지 일만 담고, "끝났다는 기준"을 적는다.
- 라벨은 타입 1개(`feat`, `fix`, `exp` 등)와 범위 1개(`pipe`, `mq`, `shm`, `server`, `client`, `bench`)를 붙인다.
- `[Experiment]`에는 가설, 바꾼 옵션 하나, 결과를 남긴다. 보고서 6.4절과 6.5절의 근거가 된다.

## 브랜치

```text
<타입>/<이슈번호>-<짧은-설명>      예: feat/12-pipe-transport, fix/20-mq-cleanup, docs/7-prediction
```

`main`에 바로 푸시하지 않는다.

## 커밋

```text
<타입>: <한 줄 요약>
```

- 타입은 영어 소문자, 요약은 한국어로 쓴다. 50자 안팎, 마침표 없이 "무엇을 했다"로 쓴다.
- 한 커밋에는 한 가지 일만 담는다. 본문이 필요하면 한 줄 띄우고 "왜"를 쓴다.
- 범위를 밝히고 싶으면 `feat(pipe): ...`처럼 괄호로 붙인다. 필수는 아니다.
- 처음 한 번 `git config commit.template .gitmessage`를 실행하면 커밋할 때 안내가 뜬다.

| 타입 | 언제 | 예 |
| --- | --- | --- |
| `feat` | 기능 추가 | `feat: FIFO 요청 채널 구현` |
| `fix` | 버그 수정 | `fix: 종료 시 메시지 큐가 남는 문제 수정` |
| `perf` | 성능 개선 (보고서 6.5절 대상) | `perf: 전역 락을 타일별 락으로 변경` |
| `refactor` | 동작이 같은 코드 정리 | `refactor: 워크로드 생성기를 함수로 분리` |
| `test` | 검증 코드 | `test: 세 버전 체크섬 일치 검사 추가` |
| `exp` | 측정 실행과 원자료 추가 | `exp: 1단계 메시지 크기별 지연 측정` |
| `docs` | 문서 | `docs: 워크로드 명세와 성능 예측 작성` |
| `build` | Makefile, CI | `build: verify 대상 추가` |
| `chore` | 그 밖의 잡일 | `chore: .gitignore 에 pgm 추가` |

`exp`는 표준 타입이 아니고 이 프로젝트에서만 쓴다. 측정 커밋을 따로 찾기 쉽게 하려는 것이다.

## PR

- 제목은 커밋과 같은 형식으로 쓴다. 예: `feat: pipe 전송 계층 구현`
- 본문 첫 줄에 `Fixes #이슈번호`를 써서 이슈와 연결한다.
- 합치기 전에 CI가 통과해야 하고, 다른 팀원 1명이 확인한다.
- `include/`의 두 헤더를 바꾸는 PR은 세 사람이 모두 확인한다.

## 넣지 않는 것

커밋 메시지, PR, 이슈에 AI 도구의 서명(`Co-Authored-By`, 생성 도구 표시, 세션 링크)을 넣지 않는다. AI 사용 사실은 [AI 활용 기록](docs/ai-log.md)에 적는다.
