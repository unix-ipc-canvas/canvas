# 테스트 명세

검증 범위·방법·판정 기준을 관리한다. 무엇을 만족해야 하는지는 [요구사항](../func-specs/README.md), 구조와 남은 작업은 [구현 계획](../tech-specs/README.md)을 따른다. 테스트 실행 명령은 [루트 README](../../README.md#테스트)에서 관리한다.

여기서 다루는 것은 "프로그램이 맞게 동작하는가"다. "얼마나 빠른가"는 테스트가 아니라 측정이며 [측정 방법](../tech-specs/02-measurement.md)을 따른다.

## 검증 전략

[verify.sh](../../scripts/verify.sh)가 항목마다 PASS, FAIL, SKIP을 출력한다. CI는 PR과 `main` 푸시마다 이 스크립트를 실행한다. 지금은 빌드 검사(T-01~T-03)와 남은 자원 검사(T-20)만 들어 있고, 실행이 필요한 항목은 서버·클라이언트 구현(T4 단계)과 함께 서버 담당이 추가한다.

### 빌드와 구조

| 번호 | 요구사항 | 확인 내용 | 방법 |
| --- | --- | --- | --- |
| T-01 | C-1, C-7 | `make` 전체 빌드가 경고 없이 통과한다 | `make EXTRA_CFLAGS=-Werror` |
| T-02 | C-7 | `make pipe`, `make mq`, `make shm`이 각각 그 버전만 빌드한다 | 버전마다 빈 상태에서 빌드 |
| T-03 | C-6 | `src/common/`, `src/bench/`에 IPC 고유 호출이 없다 | `msgsnd`, `shmat`, `mkfifo` 등을 검색 |

## 결과 판정

- FAIL은 0이어야 한다. FAIL이 있으면 PR을 합치지 않는다.
- SKIP은 검증 완료가 아니다. 사유를 남기고, 해당 기능을 구현한 PR에서 검사를 추가해 없앤다.
- 제출 전에는 측정용 컴퓨터에서 SKIP 0, FAIL 0을 확인하고 그 출력을 보고서 5.3절의 근거로 쓴다.
- T-13은 판정 항목이 아니라 시연 항목이다. 결과(어긋난 횟수 / 실행 횟수)를 보고서 4.3절에 쓴다.

## 수동 확인

자동화하지 않고 제출 전에 사람이 한 번 확인한다.

- Ubuntu + gcc 환경의 깨끗한 폴더에서 `make dist`로 만든 tar를 풀어 `make`가 통과하는지
- `readme.txt`의 순서대로 따라 했을 때 실행과 측정 재현이 되는지
- `ipcs` 결과 화면을 캡처했는지
