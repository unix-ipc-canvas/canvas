# 설계 메모

구현하면서 지켜야 할 기술 약속을 모아 둔 문서입니다. 쉬운 설명은 팀 안내서를 보세요.
상태: **초안**. 11/13까지 팀이 확정합니다. 확정 뒤에 바꾸면 아래 "변경 기록"에 적습니다.

## 1. 구성

```
클라이언트 프로세스 × N                     서버 프로세스
┌──────────────┐   요청 채널 (공용, N:1)   ┌─────────────────────┐
│ 송신 스레드  │ ────────────────────────▶ │ 수신 스레드         │
│ 통계 스레드  │                           │   ↓ 작업 큐         │
│ 수신 스레드  │ ◀──────────────────────── │ 워커 스레드 × N     │
└──────────────┘   응답 채널 (클라이언트별) │   ↕ 캔버스 (타일 락)│
                                            │ 관리 스레드         │
                                            └─────────────────────┘
```

IPC 버전마다 바뀌는 것은 두 채널뿐입니다. 나머지는 같은 코드입니다.

| `src/common/verify.c` | 정답 체크섬 계산 (단일 스레드 재생) | 클라이언트 담당 |

## 3. 채널 구조 (세 버전 공통)

- 요청 채널: 공용 1개. 모든 클라이언트가 쓰고 서버 수신 스레드 하나가 읽습니다.
- 응답 채널: 클라이언트마다 1개. 워커들이 쓰고 그 클라이언트의 수신 스레드가 읽습니다.

| | 요청 채널 | 응답 채널 | 큰 응답 처리 |
| --- | --- | --- | --- |
| pipe | `/tmp/osproject_<팀>_req` FIFO | `/tmp/osproject_<팀>_resp_<id>` FIFO | write 반복. 클라이언트별 송신 mutex로 섞임 방지 |
| mq | key 60xx0 큐 | key 60xx1 큐 하나, mtype = client_id + 1 | 조각으로 나눠 보내고 재조립. 클라이언트별 송신 mutex |
| shm | key 60xx2 영역의 링 버퍼 + 세마포어 | key 60xx3 영역의 클라이언트별 슬롯 + 세마포어 | 슬롯에 한 번 복사 |

알아 둘 한계
- 요청은 모두 4096B(PIPE_BUF) 이하라서 FIFO에 여러 클라이언트가 동시에 써도 섞이지 않습니다. 응답은 그보다 클 수 있어 송신 락이 필요합니다.
- System V 메시지 하나는 기본 8192B(msgmax), 큐 하나는 기본 16384B(msgmnb)까지입니다. 값을 올려서 측정할지 기본값으로 측정할지는 1단계에서 정하고 이유를 보고서에 씁니다.
- mq 응답 큐를 클라이언트별로 따로 둘지, 하나를 mtype으로 나눠 쓸지는 mq 담당이 1단계에서 재 보고 정합니다.

## 4. 캔버스와 락

- 1024 × 1024, 한 칸 1바이트. 64 × 64 타일 256개.
- 타일 번호 = `(y / 64) * 16 + (x / 64)`.
- 여러 타일에 걸친 요청은 **타일 번호 오름차순**으로 락을 잡습니다 (교착 상태 방지).
- DRAW는 덮어쓰기가 아니라 **더하기 (mod 256)** 입니다. 순서와 무관하게 결과가 같아야 체크섬 검증이 성립합니다.

락 방식은 서버 옵션으로 고릅니다.

| 옵션 | 내용 | 용도 |
| --- | --- | --- |
| `global` | mutex 1개 | 기준선 (처음 구현) |
| `tile` | 타일별 mutex | 개선 실험 |
| `tile-rw` | 타일별 rwlock (DRAW 쓰기, SNAPSHOT 읽기) | 개선 실험 |
| `none` | 락 없음 | 경쟁 상태 시연 전용 |

## 5. 실행 옵션 (모든 설계 선택은 옵션으로)

원인 분석 실험은 "옵션 하나만 바꿔 다시 돌리기"로 합니다. 코드를 고쳐서 실험하지 않습니다.

서버
- `-w N` 워커 수
- `-l global|tile|tile-rw|none` 락 방식
- `-d` 수신 스레드가 큐를 거치지 않고 직접 처리 (큐 비용 확인용)

클라이언트
- `-i ID` 클라이언트 번호, `-s SEED` 시드, `-n N` 요청 수
- `-m PCT` DRAW 비율(%), 나머지는 SNAPSHOT
- `-r SIZE` DRAW 사각형 한 변, `-S SIZE` SNAPSHOT 영역 한 변
- `-f N` 동시에 띄워 둘 요청 수 (1 = 지연 측정, 크게 = 처리량 측정)
- `-o FILE` 결과 CSV 경로

같은 시드면 세 버전이 받는 요청열이 완전히 같아야 합니다.

## 6. 측정

- 시각: `clock_gettime(CLOCK_MONOTONIC)`. 측정 구간 안에서는 출력하지 않습니다.
- 구간 분해: 응답에 실린 `srv_ts_t`로 요청 전송, 큐 대기, 락 대기, 처리, 응답 전송을 따로 기록합니다.
- 통계: 평균, 중앙값, 상위 99%, 최대. 조건마다 워밍업 후 요청 수천 건 이상.
- 자원: `getrusage()`의 CPU 시간과 컨텍스트 스위치(자발적, 비자발적), `/proc/self/status`의 VmRSS.
- 모든 측정은 측정용 컴퓨터 1대에서 합니다. 원자료 CSV는 `results/`에 커밋합니다.

## 7. 종료와 자원 정리

- 서버 관리 스레드가 `sigwait`로 SIGINT, SIGTERM을 받습니다. 다른 스레드는 이 신호를 막아 둡니다.
- 종료 순서: 수신 스레드 깨우기(`tp_server_wake`) → 워커 종료 → 캔버스 PPM 저장과 체크섬 출력 → `tp_server_close`.
- 실행 후 `ipcs`에 우리 key가 남아 있으면 버그입니다.
