# 테스트 명세 — 다중 그림판 공유 캔버스 서버

[문서 안내](../../README.md#관련-문서)

`make test`(`scripts/verify.sh`)가 아래 항목을 이 번호로 실행하고 PASS·FAIL·SKIP을 출력한다. 각 항목의 괄호는 확인하는 요구사항이다. 문서 검사(T-00)가 요구사항 번호가 모두 여기에 대응되는지, 이 표와 `verify.sh`의 번호가 같은지 확인한다. 실행 명령은 [README의 테스트](../../README.md#테스트)에 있다.

- SKIP은 검증 완료가 아니다. 실행 파일이 없거나, 그 환경에서 돌릴 수 없는 항목(예: ThreadSanitizer를 쓸 수 없는 커널)만 SKIP이다.
- 우리 서버가 떠 있지 않을 때 돌린다. 모든 항목이 끝나면 남은 자원을 검사한다(T-20).

## 빌드와 구조

| 번호 | 항목 | 판정 기준 |
| --- | --- | --- |
| T-00 | 문서 검사 (C-10) | 문서의 링크와 앵커가 살아 있다. 요구사항 번호가 모두 이 문서에 나온다. 이 표와 `verify.sh`의 번호가 같다. 성능 예측이 `작성 완료` 상태다 |
| T-01 | 경고 없는 전체 빌드 (C-1, C-4) | `make EXTRA_CFLAGS=-Werror`가 성공한다 |
| T-02 | 버전별 빌드 (C-4, C-7) | `make pipe`, `make mq`, `make shm`, `make upipe`가 각각 성공한다 |
| T-03 | 공통 코드에 IPC 고유 호출 없음 (C-7) | `src/common`, `src/bench`, `src/test`에 `msgget`, `shmat`, `semop`, `mkfifo` 등이 없다 |
| T-04 | 전송 계층 시험 | `scripts/test-transport.sh`가 세 IPC 모두 통과한다(1단계 시험) |
| T-05 | 1단계 벤치마크 내용 검사 | `bench_<ipc> -V`가 모든 응답의 내용을 확인하고 성공한다 |

| T-26 | 설계 개선 모드 (N-6, N-3, N-4) | mq 응답 큐 8개 + 요청 큐 입장 제한(`OSP_MQ_RESP_Q=8 OSP_MQ_ADMIT=1`), shm 클라이언트별 요청 링(`OSP_SHM_REQ=per`), pipe 응답 FIFO 키우기 + 송신 스레드(`OSP_PIPE_GROW=1 OSP_PIPE_ASYNC=1`)와 송신 스레드만(`OSP_PIPE_ASYNC=1`, FIFO가 작아 나머지가 실제로 생긴다), pipe 원인 확인 모드(`OSP_PIPE_RBUF=1 OSP_PIPE_RESP_SZ=131072`. 클라이언트 1024개에서는 사용자별 한도로 키우기가 거부되는 경로도 지난다)로 서버를 띄워, 전송 계층 시험 23개(T-04), 클라이언트 4개(T-10)와 1024개 × 그림판 8개(T-23)의 체크섬 = 검증기, 클라이언트를 `kill -9` 한 뒤 같은 번호로 다시 접속해 끝까지 동작하는지 본다 |

## 시작 구간 경쟁

`make test`에 넣지 않은 재현 실험이다(`scripts/race-start.sh`. CPU 부하를 걸어 몇 분 걸린다). 재수행 PR의 CI에서 T-22(pipe)가 한 번 실패한 원인을 찾다가 만들었다. 찾은 원인은 둘이다.

**1. 시험 도구의 경쟁 (CI 실패의 직접 원인).** `verify.sh`의 `start_server`는 `srv.err`에 '시작'이 찍히면 서버가 떴다고 보았다. 그런데 그 파일을 비우는 리다이렉션은 백그라운드 자식이 하므로, 자식이 늦게 돌면 직전 시험(T-19) 서버가 남긴 '시작' 줄을 보고 바로 넘어간다. 그러면 T-22의 두 번째 서버가 첫 서버보다 먼저 자리를 잡아, 두 번째 서버가 10초 동안 떠 있다가(rc=124) 끝나며 자원을 지우고, 첫 서버(이미 '서버가 이미 떠 있다'로 끝남)의 클라이언트가 실패한다(rc=1). 로컬에서는 100번, CPU 부하 12에서 100번 모두 재현되지 않아, 자식의 리다이렉션만 0.2초 늦추는 조건을 넣어 재현했다.

| 판정 | 자식 리다이렉션 0.2초 지연 | 결과 |
| --- | --- | --- |
| '시작' 줄이 있으면 (수정 전) | pipe 4번, mq 2번, shm 2번 | 모두 CI와 같은 모양으로 실패 (두 번째 서버 rc=124, 클라이언트 rc=1) |
| 이 서버의 pid가 찍힌 '시작 (pid N,' 줄만 (수정 후) | pipe 4번 | 실패 0 |

`scripts/app-bench.sh`도 같은 판정을 쓰고 있어 함께 고쳤다.

**2. pipe 전송 계층의 TOCTOU.** 위 원인 말고도 서버 둘이 함께 뜰 수 있는지 보려고 서버 둘을 같은 순간에 띄워 보다가 찾았다. FIFO가 이미 있으면 '읽는 쪽이 없으면 비정상 종료가 남긴 파일'로 보고 지운 뒤 다시 만드는데, 만든 쪽이 읽기 끝을 열기 전에 같은 이름을 쓰는 다른 프로세스가 판정하면 막 만든 FIFO를 지운다. 실험 조건은 아래와 같고, 바꾼 것은 CPU 부하(바쁜 루프 12개 = 논리 CPU 수) 하나다.

- 실험 A: 서버 둘을 같은 순간에 띄우고 0.3초 뒤 살아 있는 서버 수를 센다. 정확히 하나여야 한다.
- 실험 B: 서버 하나에 같은 번호(7) 클라이언트 둘을 같은 순간에 띄운다(각 요청 100,000개). 하나만 거부되어야 한다.

| 실험 | IPC | 부하 | 수정 전 (11/27) | 수정 후 (11/28, 각 60번) |
| --- | --- | --- | --- | --- |
| A 서버 둘 | pipe | 0 | 150번 모두 하나 | |
| A 서버 둘 | pipe | 12 | 150번 중 **둘 다 뜸 21번, 둘 다 실패 3번** | 모두 하나 |
| A 서버 둘 | mq, shm | 0, 12 | 각 150번 모두 하나 | 모두 하나 |
| B 같은 번호 클라이언트 둘 | pipe | 0 | 60번 모두 하나만 거부 | |
| B 같은 번호 클라이언트 둘 | pipe | 12 | 60번 중 **4번 둘 다 멈춤**(타임아웃으로 강제 종료) | 모두 하나만 거부 |
| B 같은 번호 클라이언트 둘 | mq, shm | 12 | 재지 않음(이 수정과 무관) | 모두 하나만 거부 |

- 둘 다 멈춘 두 클라이언트의 `/proc/<pid>/fd`가 같은 inode(28184)의 `/tmp/osproject_2_resp_7`을 가리켰다. 한쪽이 FIFO를 지우고 다시 만든 뒤 다른 쪽이 경로로 열어, 응답 FIFO 하나를 둘이 읽으며 응답이 엇갈린 것이다.
- 고친 방법: "판정 → 지우고 다시 만들기 → 읽기 끝 열기"를 잠금 파일 `/tmp/osproject_2_req.lock`의 `flock`(시작 잠금)으로 묶었다([설계의 공유 자원과 동기화](../design/README.md#공유-자원과-동기화)). mq·shm은 처음부터 잠금 파일의 바이트 잠금으로 서버 자리를 먼저 잡고 시작해 이 문제가 없었다.
- 실행: `scripts/race-start.sh -n 60 -l 12 pipe mq shm` (수정 전 결과는 11/27의 같은 내용 임시 스크립트로 쟀다).
